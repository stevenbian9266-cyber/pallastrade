基于你现在已经核实的代码现状，P0 应该从“重构支付体系”收敛为 **Payment Foundation Hardening**：保留现有 `PaymentSession → Gateway → Stripe → Carts::Complete` 主链，只修确定存在的可靠性、安全性和未来演进阻塞点。

现有系统已经完成了相当多支付抽象：Stripe SDK 被锁在 `pallastrade_stripe`，标准主链通过 `PaymentSessions::Start`、Gateway 和 `Carts::Complete` 收敛，不能再按“从零建设 Payment Domain”的假设去重写。

# 三、P0-0：先建立支付回归安全网

这是所有代码修改之前的第一任务。

现有标准支付已经有 Order lock、active session reuse、`operation_key`、Stripe idempotency 和 `Carts::Complete` 单点完成入口，这些都是不能破坏的核心资产。

## 要实现

补齐自动化测试，至少锁死：

```text
Standard Payment Start

重复 Start
并发 Start
相同 operation_key
Stripe idempotency

API complete

Webhook complete

Redirect fallback

重复 complete

API complete + Webhook 并发

Webhook + Redirect 并发

PaymentSession completed 重复处理

Payment 创建唯一性

订单不重复 finalize

Stripe amount mismatch

Stripe currency mismatch

cs_ Checkout Session 模式

pi_ PaymentIntent 模式
```

特别要覆盖：

```text
Session.external_id = cs_xxx
Payment.response_code = pi_xxx
```

的真实场景。

## 完成标准

必须满足：

```text
同一支付意图重复调用 Start
→ 不重复创建有效支付

同一 PaymentSession 重复 complete
→ 不重复创建 Payment

API complete + Webhook 同时发生
→ Order 只完成一次

Stripe 金额和本地不一致
→ Order 不能完成

Currency 不一致
→ Order 不能完成
```

并保存一份：

```text
P0_BEFORE_REFACTOR_TEST_BASELINE
```

记录当前通过用例。

# 四、P0-1：PaymentSession ↔ Payment 正式关联

这是当前最应该先解决的数据模型问题。

现状是：

```text
Payment.response_code
↔
PaymentSession.external_id
```

通过字符串关联，而且没有 FK。现有分析明确确认了这一点。

现在又进一步确认：

```text
Checkout Session mode:

PaymentSession.external_id = cs_xxx

Payment.response_code = pi_xxx
```

因此两者不能继续承担实体关系。

## 要实现

优先方案：

```text
pallastrade_payments
新增：

payment_session_id
```

关系：

```text
Payment
belongs_to :payment_session
optional: true

PaymentSession
has_one :payment
```

并逐步改造：

```text
find_or_create_payment!
```

使其显式传入：

```text
payment_session
```

最终：

```text
Payment.payment_session_id
=
内部关联

Payment.response_code
=
PSP reference
```

## Migration 要求

第一阶段：

```text
payment_session_id NULLABLE
```

不要立即 `NOT NULL`。

需要尝试安全回填历史数据：

### pi_ 模式

若：

```text
payment.response_code == session.external_id
```

可以直接回填。

### cs_ 模式

不要猜。

需要根据：

```text
order_id
payment_method_id
amount
session timing
provider metadata
Stripe PI / Session relation
```

判断是否可以可靠回填。

不能可靠确定的历史数据：

```text
保持 NULL
```

不要硬关联。

## 唯一约束

新数据稳定后考虑：

```text
UNIQUE(payment_session_id)
WHERE payment_session_id IS NOT NULL
```

但必须先验证：

> 当前生产语义是否确实永远是一个 Session 最多产生一个 Payment。

文件里已经有过打破 session/payment 关系导致严重问题的历史教训，因此这一点必须保守实施。

## 完成标准

新创建支付必须满足：

```text
Payment.payment_session_id != NULL
```

并且：

```text
Payment.response_code
```

不再用于定位 PaymentSession。

代码搜索要求：

```text
不能再新增：
response_code == payment_session.external_id

不能再新增：
find session by payment.response_code
```

旧兼容代码如必须保留：

```text
明确标记 LEGACY_COMPATIBILITY
```

# 五、P0-2：Webhook Event Store + Retry

这是整个 P0 最重要的可靠性建设。

现有 Webhook 已经正确做到：

```text
API Endpoint
→ Stripe 验签
→ HandleWebhookJob
→ Payments::HandleWebhook
→ Carts::Complete
```

而且没有直接修改 Order。

但当前缺失的是：

```text
事件事实
数据库级去重
失败重试
失败可见性
```

文件也明确指出没有 `payment_webhook_events`。

## 新增表

建议：

```text
pallastrade_payment_webhook_events
```

字段：

```text
id

provider
payment_method_id

provider_event_id
event_type
provider_created_at

payload

status

attempt_count

received_at
processing_at
processed_at

last_error_class
last_error_message

created_at
updated_at
```

状态：

```text
received
processing
processed
failed
```

唯一索引：

```text
UNIQUE(provider, provider_event_id)
```

## 新处理流程

```text
Stripe Webhook
↓
Verify Signature
↓
Parse provider event id
↓
INSERT WebhookEvent

duplicate?
├─ YES
│   └→ HTTP 200
│
└─ NO
    ↓
 enqueue HandleWebhookJob
    ↓
 status = processing
    ↓
 existing Payments::HandleWebhook
    ↓
 success
    ↓
 processed
```

失败：

```text
exception
↓
status = failed
↓
save error
↓
raise
↓
Job retry
```

## 异常处理必须改

禁止继续：

```text
rescue StandardError
  Rails.error...
  # swallow
end
```

建议：

```text
rescue KnownNonRetryablePaymentError => e
  mark_failed(e)
  # 明确策略

rescue StandardError => e
  mark_failed(e)
  raise
end
```

## 30 秒延迟

可以保留。

但必须在代码/文档说明：

```text
30s delay
=
降低 API complete / Webhook 竞态

NOT
=
事件顺序保证
```

## Replay 能力

P0 可以先建设 Service：

```text
Payments::ReplayWebhookEvent
```

后台按钮可以 P0.6 再接。

Replay 必须：

```text
使用同一事件记录
增加 attempt_count
写 audit
走同一 HandleWebhook
```

不能制造一个新的假 Webhook。

## 完成标准

测试必须证明：

```text
同一 provider_event_id
重复请求 10 次
→ 只有 1 条 Event Record

→ 业务完成只执行一次
```

以及：

```text
Webhook 处理发生临时错误
→ Event = failed
→ Job retry

retry 成功
→ Event = processed
```

还必须支持：

```text
查 provider_event_id
→ 能知道收到没收到
→ 处理成功没成功
→ 为什么失败
```

# 六、P0-3：Express Checkout 幂等加固

当前 Standard order-domain Start 已经很强：

```text
Order lock
+
active session reuse
+
operation_key
+
Stripe idempotency
```

而 Legacy/cart Express create 比较弱。

目前三套 Stripe 前端能力并存，ExpressCheckoutElement 仍然是实际活跃能力。

## 目标

把 Express 至少提升到：

```text
同一业务意图
+
重复点击
+
重复网络请求
=
一个有效 provider payment
```

## 要实现

先分析 Express 当前业务 key。

推荐建立稳定：

```text
operation_key
```

例如：

```text
express:{cart/order reference}:{attempt}
```

不要使用随机值作为 Stripe idempotency key。

实现：

```text
Lock business aggregate
↓
Find reusable active session
↓
Determine operation_key
↓
Unlock DB transaction
↓
Provider call with idempotency key
↓
Persist result
```

复用 Standard `PaymentSessions::Start` 能力优先于重新写一套。

如果 Express 当前结构不允许直接复用：

```text
提取 shared idempotency service
```

但不要反过来大规模重写 Standard。

## 完成标准

自动化测试：

```text
Express 用户连续点击 5 次
→ Stripe 创建 1 个有效 payment

两个并发 HTTP request
→ 1 个有效支付

第一次 provider timeout
客户端 retry
→ 不产生重复扣款
```

# 七、P0-4：Express 服务端金额权威化

标准主流程已经基本正确：

```text

→ Money
→ Stripe
```

当前真正需要解决的是 Express 前端重算问题。

## 目标

最终：

```text
Server
=
唯一支付金额权威

Frontend
=
展示 + 传递
```

## 新增/调整后端响应

例如：

```json
{
  "currency": "USD",
  "amount": 10549,
  "display_total": "$105.49",
  "line_items": [
    {
      "label": "Subtotal",
      "amount": 10000
    },
    {
      "label": "Shipping",
      "amount": 699
    }
  ]
}
```

这里：

```text
amount
```

由 Backend 从：

```text
Order.amount_due
```

或者未来：

```text
CheckoutSnapshot.total
```

产生。

## 前端整改

```text
toCents(...)
buildLineItems(...)
```

作为支付金额计算逻辑。

可以保留：

```text
formatMoney
```

用于展示。

原则：

```text

```

现有支付完成时的：

```text
verify_payment_intent_matches!
```

金额 + Currency 强校验必须继续保留。

## 完成标准

代码搜索：

```text

不能由 subtotal/tax/shipping 在前端重新加总
```

测试：

```text

```

以及：

```text

→ Backend completion validation 拒绝
```

# 八、P0-5：Secret 安全迁移

现有：

```text
PaymentMethod.preferences
```

为 text/YAML，并明文保存 Secret，这是文件确认的真实安全风险。

## Secret Inventory

至少盘点：

```text
Stripe secret_key

Stripe publishable_key
是否属于 secret 视情况，不需要同 secret key 等级

Stripe webhook signing_secret

任何 gateway credential

未来已有 Adyen/PayPal credential
```

## 第一步不是立即改

先做：

```text
Encryption Compatibility Spike
```

验证：

```text
Preference DSL
YAML serialization
password type
Masking.serialize
Admin apply_preferences
STI
Existing tests
```

和 Rails Encryption 是否兼容。

## 候选方案 A

如果兼容：

```text
Encrypted preferences
```

## 候选方案 B

如果不兼容：

```text
public preferences

+

encrypted credentials
```

例如：

```text
encrypted_secret_preferences
```

## 候选方案 C

如果项目已有外部 Secret Manager：

```text
preferences
只存 secret_reference
```

优先复用现有能力。

## 迁移过程

必须渐进：

```text
Add encrypted storage
↓
dual-read
↓
backfill
↓
verify
↓
write encrypted only
↓
stop plaintext reads
↓
remove plaintext secret
```

## Key Rotation

迁移后必须输出：

```text
CREDENTIAL_ROTATION_REQUIRED
```

盘点：

```text
Stripe API Secret
Webhook signing secret
```

是否需要 Rotation。

原因是旧 DB dump / backup 已经可能保存过明文。

## 完成标准

必须做到：

```text
新数据库 dump
看不到 sk_xxx 明文

普通 Rails console inspect
不直接暴露 Secret

Admin GET
只返回 masked value

masked value 再提交
不会覆盖真实 Secret
```

并且现有 Stripe 功能测试全部通过。
