文档基础信息
一、产品概述
1.1 页面定位
Checkout页面（官方统一口径：Checkout页面 = 订单确认页）是跨境独立站从商品选购到最终支付转化的核心闭环页面，采用一体式单页设计，整合联系信息、配送地址、配送方式、增值服务、支付方式、订单摘要全模块，减少页面跳转流失。同时联动登录用户地址簿管理体系，实现下单地址自动沉淀、智能去重、默认地址迭代，完整支撑全站五大下单支付场景，适配游客/登录用户双用户体系。
1.2 核心目标
- 极简结账链路，降低操作成本，大幅提升跨境订单支付转化率
- 实时联动价格计算、配送规则、折扣税费，建立价格透明感
- 依托增值服务能力，有效提升用户客单价
- 建立标准化地址沉淀机制，自动留存有效下单地址，提升复购结账效率
- 通过地址去重、数量上限管控、默认地址智能迭代，解决地址冗余、错乱问题
- 完善接口安全、并发防重、防注入能力，保障跨境服务稳定
v1.5 全域术语统一终版（唯一口径：Checkout页面=订单确认页，全文档、流程、时序、场景100%对齐）
v1.4 全网口径统一终版（场景唯一、术语统一、规则无冲突、删除冗余废弃内容）
1.3 业务整体能力说明（含统一场景口径）
本体系支撑全站五大标准下单场景：A加购结算、B立即购买、C购物车结算、D个人中心二次支付、E邮件订单回流补付。严格区分游客/登录用户权限，包含表单校验、订单创建、异步数据同步、支付网关对接、全局邮件通知、安全并发防护、下单地址自动沉淀+地址簿全生命周期管理全链路能力，形成「下单-支付-地址沉淀-地址管理」完整闭环。全局唯一固化口径：所有前台新建订单场景（A/B/C/E）均走【Checkout订单确认页】；仅D场景走独立微收银台，不进入Checkout订单确认页链路。
1.4 名词定义（地址管理体系+跨境双地址体系）
本章节统一全站地址相关名词口径，区分跨境场景收货地址、账单地址双体系，所有页面、接口、流程严格遵循本定义，无特殊例外。

二、全局强制核心业务规则（含地址管理R1-R10铁规）
本章节为全站下单、支付、地址管理通用最高优先级规则，所有页面、接口、流程严格遵从。
2.1 通用下单支付规则
- 双身份下单规则：支持游客未登录、登录用户两种下单模式；游客可完整走A/B/C/E场景下单支付流程，无需强制登录；登录用户下单自动绑定账号信息；D场景待支付订单二次支付仅登录用户可用，游客无个人中心订单、地址簿体系，仅支持E场景邮件回流补付。
- 场景核心区分规则：A/B/C三大前台场景需触发订单创建；D场景为已有订单支付，仅唤起支付、不重复创建订单。
- 订单创建幂等规则：同一下单流程仅创建一次订单，支付失败、取消后重新支付，禁止重复建单，强制复用原有订单。
- 订单同步差异化规则：仅登录用户订单创建成功后，异步同步订单数据至个人中心订单模块，不阻塞主支付流程；游客订单无个人中心数据同步逻辑。
- 全局邮件通知规则（修复版）：不区分游客/登录用户、不区分登录态，只要用户在Checkout订单确认页填写有效邮箱，订单创建成功、支付成功、支付失败、支付取消所有关键节点，均异步触发对应邮件通知；无有效邮箱则不发送，异步执行不阻塞下单、支付主流程。登录用户默认带入账号绑定邮箱，游客手动填写邮箱即可接收订单全量通知，保障游客订单知情权。
- 安全并发防护规则：所有下单、订单创建接口强制增加安全校验、并发防重、非法请求拦截、防指令注入能力，规避恶意攻击、并发异常导致的服务瘫痪。
- 流程终止规则：订单创建失败时，直接终止全流程，不进入任何支付环节、不触发地址保存。
- 结果页统一规则：所有支付结果（成功/失败/取消）最终统一落地订单支付结果页，标准化展示结果与操作按钮。
2.2 地址管理强制规则（R1-R10 最终确认口径）
- R1 地址保存触发规则：地址簿入库唯一触发条件为订单创建成功；仅收货地址参与沉淀入库，账单地址不保存、不沉淀、不进入地址簿；订单失败、取消、超时、未支付完成的地址一律不入库；已保存地址不会因订单取消回滚。
- R2 地址去重规则：仅收货地址入库/编辑保存前按标准化去重键比对，命中重复则复用已有记录、不新增；地址标签、账单地址信息均不参与去重比对。
- R3 默认地址入口规则：个人中心地址卡片仅针对收货地址提供「设为默认」操作入口，账单地址无默认配置功能。
- R4 默认地址唯一规则：用户维度任意时刻仅存在1条默认收货地址，设置新默认时自动取消原有默认标记；账单地址无唯一默认逻辑。
- R5 地址数量上限规则：单用户收货地址簿有效地址上限20条，满额禁止新增收货地址；账单地址不占用名额、无数量限制。
- R6 前端超限拦截规则：地址管理页收货地址数≥20时，拦截「添加地址」操作，弹窗提示「最多20个地址，请先删除一些弃用地址」，禁止进入新增收货地址流程；账单地址新增无超限拦截。
- R7 下单兜底超限规则：订单创建成功后异步校验收货地址数量，若已达20条，静默不保存本次新收货地址，不影响订单与支付主流程、不影响账单地址提交。
- R8 首地址自动默认规则：用户首次保存收货地址至空地址簿时，系统自动设为默认收货地址，符合唯一默认规则。
- R9 删除默认自动提升规则：删除当前默认收货地址后，剩余收货地址按「最近使用优先、无使用记录则最早创建优先」自动提升为新默认地址；无剩余地址则置空默认状态；账单地址无此逻辑。
- R10 编辑地址合并规则：仅收货地址编辑保存后，若与已有地址去重键重合，自动合并复用已有记录（保留默认标记、使用记录），丢弃当前编辑条目，不新增冗余地址；账单地址编辑提交不触发合并、去重逻辑。
- R11 跨境双地址隔离规则（新增）：系统严格区分收货地址、账单地址两套地址体系：收货地址纳入用户地址簿全生命周期管理，可沉淀、可复用、可设默认、有限额；账单地址为订单/支付单次维度数据，仅随当前订单留存订单快照，不全局保存、不跨单复用、不展示在个人中心地址列表。
- R12 双地址复用规则（新增）：Checkout页面默认开启「账单地址同收货地址」，一键复用数据，减少用户填写；用户可手动取消勾选，独立填写专属账单地址，适配跨境支付风控核验要求。

场景E：全量用户邮件待付款订单回流支付（游客/登录通用·最终统一口径）
场景定义（全局唯一标准）：适配全站所有A/B/C场景生成的未支付有效订单，不区分游客、登录用户，用户在订单通知邮件内点击支付链接，直接打开Checkout订单确认页恢复订单并完成补付。核心统一口径：邮件回流页面不校验前端实时登录态，仅以订单后台原始UID绑定关系判定订单归属与权限，支持未登录补付、跨账号代付，不迁移订单归属。
核心落地规则
- 页面访问规则：无论用户当前浏览器是否登录、登录账号是否与订单归属一致，只要链接参数合法、订单状态为待支付、订单未过期，均可正常打开Checkout订单确认页完成补付。
- 订单归属判定规则：游客订单：后台无UID绑定，仅关联下单预留邮箱，支持任意合法链接设备补付，无账号关联；登录用户订单：后台绑定创建人UID，支付完成后订单归属永久锁定原创建账号，不随当前操作登录态迁移，支持未登录补付、跨账号代付。
- 页面数据回填规则：打开页面自动还原订单快照全量数据，包含联系邮箱、收货地址、账单地址、商品清单、配送方式、增值服务、价格明细；支持用户手动修改收货地址、账单地址、配送方式等可编辑项，修改后实时重算价格并更新订单快照。
- 地址沉淀差异化规则：回流支付成功后，仅原订单为登录用户创建的订单，触发收货地址异步沉淀、去重、数量校验等全套地址簿规则；游客订单、跨账号代付订单，均不触发任何地址簿读写与沉淀逻辑。
- 邮件通知规则：支付成功/失败/取消结果，统一推送至订单创建时预留的原始邮箱，与当前操作人无关，保障订单所有者知情权。
- 拦截规则：已支付、已关闭、已过期、参数伪造、非法篡改的订单链接，直接拦截页面访问，统一提示「订单无效或已结束」。
完整标准流程
- 用户（游客/登录）通过前台A/B/C场景下单创建未支付订单，系统向预留邮箱发送订单创建通知邮件；
- 用户在任意设备打开邮件，点击订单支付链接，携带订单唯一校验参数访问Checkout页面；
- 后台校验链接参数合法性、订单状态、订单有效期，校验失败直接拦截，校验通过则放行Checkout订单确认页页面；
- 页面无视当前前端登录态，自动还原订单历史全量快照数据，完成页面初始化；
- 用户可按需修改收货地址、账单地址、配送方式等信息，系统实时重算订单价格、税费并更新快照；
- 用户确认信息后提交支付，唤起对应支付网关，完成支付操作；
- 支付回调完成后，更新订单状态，异步发送支付结果邮件，严格按订单原始身份执行地址沉淀、数据同步逻辑，最终跳转支付结果页。

七、核心业务计算逻辑
7.1 订单金额计算链路（强制标准）
商品小计 − 折扣金额 + 增值服务费 + 运费 + 预估税费 = 订单总金额
计算优先级：先扣折扣、再计算税费，税费基数为折扣后金额，税率根据收货地址国家/地区动态获取。
7.2 配送决策逻辑
整单配送方式 = 所有单品支持配送方式的交集，运费与时效由配送方式、收货地址、商品属性综合计算。
7.3 折扣与税费规则
- 百分比折扣基于商品小计计算，固定金额折扣直接抵扣小计
- 税费为预估税费，最终金额以发货时系统结算为准
- 同一订单仅支持单个折扣码/礼品卡
八、支付结果页交互规则
- 支付成功：展示【继续购物】按钮，跳转全站商品列表页
- 支付失败：展示【重新支付】按钮，复用原订单唤起支付，禁止新建订单
- 支付取消：默认展示结果页，无强制操作按钮，静默展示订单状态

    %% 2.跳转结账页、填写邮箱与配送地址
    Page->>Page: 完成选购，跳转Checkout结账页
    Note over Page: 登录用户自动回填绑定邮箱游客手动填写邮箱邮件通知规则完全一致，仅校验有效邮箱

    %% 3.提交下单、创建订单
    User->>Page: 确认信息点击 pay now
    Page->>Server: 提交下单请求（携带页面填写邮箱）
    Server->>Server: 安全校验、库存校验、订单创建
    alt 订单创建失败
        Server-->>Page: 返回失败，流程终止
    else 订单创建成功
        Server-->>Page: 返回订单信息、支付参数

        %% 4.差异化：仅登录用户同步订单至个人中心（游客无此能力）
        opt 仅已登录用户
            Server->>UserCenter: 异步同步订单至个人中心
        end

        %% 5.核心补齐：显性区分游客/登录，统一触发订单创建邮件
        rect rgb(232,245,233)
        Note over Server,MailServer: 【核心规则】游客/登录用户平等，有有效邮箱即发建单邮件
        alt 当前为游客用户 && 订单含有效邮箱
            Server->>MailServer: 异步发送【游客-订单创建成功】邮件
        else 当前为登录用户 && 订单含有效邮箱
            Server->>MailServer: 异步发送【登录用户-订单创建成功】邮件
        end
        end

        %% 6.差异化：仅登录用户执行地址沉淀逻辑（游客无地址簿）
        opt 仅已登录用户
            Server->>AddrServer: 触发地址异步保存事件
            AddrServer->>AddrServer: 地址标准化、去重匹配(R2)
            alt 地址重复
                AddrServer->>AddrServer: 复用已有地址，不新增
            else 地址不重复
                AddrServer->>AddrServer: 校验地址数量上限(R5/R7)
                alt 地址已满20条
                    AddrServer->>AddrServer: 静默不保存，不影响订单
                else 名额充足
                    AddrServer->>AddrServer: 保存新地址
                    AddrServer->>AddrServer: 首条自动设为默认(R8)
                end
            end
        end

        %% 7.唤起支付、获取结果
        Page->>PayServer: 唤起支付网关
        PayServer-->>Page: 返回支付结果（成功/失败/取消）

        %% 8.全局统一支付结果邮件通知（游客/登录平等）
        Server->>MailServer: 校验订单有效邮箱，异步发送【支付结果】邮件

        Page->>Page: 统一跳转支付结果页
    end

    %% 9.结果页交互
    alt 支付成功
        User->>Page: 点击继续购物，跳转商品列表
    else 支付失败
        User->>Page: 点击重新支付，复用原订单重试
    end

    %% D场景：个人中心待支付订单二次支付（仅登录用户）
    User->>Page: 个人中心进入待支付订单
    Page->>Server: 权限+订单状态校验
    Page->>PayServer: 微收银台唤起支付
    PayServer-->>Page: 返回支付结果
    Server->>MailServer: 读取原订单留存有效邮箱，异步发送支付结果邮件
    Page->>Page: 跳转支付结果页

十一、地址管理特殊场景与边界处理
- 订单成功但地址超限：订单正常完成、支付正常流转，后端异步静默拦截新增收货地址入库，无前端弹窗、无用户感知；账单地址不受影响，正常随订单留存快照。
- 编辑地址重复：仅收货地址自动合并复用原有地址数据，保留历史使用记录与默认状态，不产生冗余数据；账单地址无去重合并逻辑。
- 删除默认地址：仅删除默认收货地址时，系统自动智能提拔新默认收货地址，保证下单始终有默认回填地址；账单地址无默认、无提拔逻辑。
- 游客下单：前台A/B/C场景下单全程不读写收货地址簿，无任何收货地址沉淀逻辑；游客邮件回流E场景补付，同样不触发地址沉淀，账单地址仅随单次订单留存，无全局存储。
- 首次下单地址：首次下单收货地址自动设为默认收货地址，下次下单自动回填；账单地址无默认复用。
- 多地址同名差异标签：仅收货地址内容参与去重，标签不影响，自动判定为同一地址并合并；账单地址不参与任何去重比对。
- 跨境双地址隔离边界：所有用户（游客/登录）的账单地址均为「订单级单次数据」，仅在当前订单快照、支付记录中留存，不进入用户私有地址库，杜绝账单地址冗余、错乱、隐私泄露问题，适配跨境合规。
- 全量用户邮件回流场景边界（E场景最终收口）：邮件链接唤起Checkout订单确认页无视前端登录态，权限、归属、数据沉淀全部以订单后台原始创建身份为准；代付、离线补付不改变订单权属、不触发异常地址沉淀。
十二、落地核心要点汇总
- 前置校验优先：所有下单请求优先完成登录态、安全、并发、防注入校验，拦截非法请求。
- 全链路异步解耦：订单同步、邮件通知、地址沉淀均为异步任务，不阻塞下单与支付主流程，页面响应更快。
- 用户身份&邮件权限&双地址隔离：游客无订单同步、无地址簿、无D场景支付权限；邮件通知完全平等，不区分游客/登录用户，仅校验订单是否预留有效邮箱，订单创建、支付全节点统一触达；系统严格隔离收货/账单双地址体系，收货地址可沉淀复用，账单地址单次使用、仅存订单快照，适配跨境电商支付风控与合规要求。
- 强幂等与数据洁净：订单不重复创建、地址自动去重合并，从源头杜绝冗余脏数据。
- 地址规则强兜底：前端拦截+后端异步双层兜底地址上限，兼顾体验与数据规范。
- 默认地址智能迭代：首次自动默认、删默认自动提拔、新默认自动覆盖旧默认，全程无需用户手动干预。
- 安全防护闭环：接口防重、防注入、地址数据标准化、权限隔离，保障系统稳定与数据规范。
