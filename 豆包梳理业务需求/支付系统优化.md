下面这版我按你当前代码真实现状重新收敛，作为 **“支付体系总体建设框架 V1”**。核心策略是：

**Stripe-first、标准链路优先、前端 Checkout 自研、敏感支付控件用 Stripe、后端金额权威、PaymentSession 继续作为当前支付会话核心、先加固再演进到 OTS / Multi-PSP。**

# PallasTrade 支付体系总体方案 V1

## 1. 总体原则

当前系统不是从零建设 Payment Center。

现有代码已经具备：

* `Payment`
* `PaymentSession`
* `PaymentMethod / Gateway`
* Stripe adapter gem
* Refund
* Webhook
* `Carts::Complete`
* Order payment state
* PaymentSession 幂等启动
* Stripe SDK 隔离

Stripe SDK 当前集中在 `pallastrade_stripe`，core/api/admin 不直接依赖 Stripe；标准支付链路已经是 Storefront → API → `PaymentSessions::Start` → Gateway → Stripe，并通过 API complete / Webhook 等路径最终收敛到 `Carts::Complete`。

因此目标不是重建 Payment Domain，而是：

```text
现有 Payment Foundation
        ↓
可靠性加固
        ↓
统一 Checkout
        ↓
Order Transaction 编排
        ↓
Stripe Production V1
        ↓
退款 / 支付运营
        ↓
Adyen
        ↓
Multi-PSP Router
        ↓
支付优化 / 对账 / 风控
```

# 5. 前端金额原则

前端永远不是资金计算 Source of Truth。

标准支付当前已经基本符合：

```text
Order.amount_due
↓
PallasTrade::Money
↓
minor unit
↓
Stripe
```

并且支付完成还有 amount + currency 的服务端校验。

最终统一规定：

```text
Backend:
subtotal
discount
shipping
tax
total
currency

        ↓

Frontend:
只展示
```

禁止：

```text
Frontend
↓
subtotal + tax + shipping - coupon
↓
生成 Stripe 应扣金额
```

特别是现有 Express Checkout 的：

```text
toCents()
buildLineItems()
```

需要逐步改为：

```text
Backend Payment Quote
↓
Frontend
↓
ExpressCheckoutElement
```

前端只能格式化，不能重新计算真实支付金额。


```text

PaymentElement
ExpressCheckoutElement
```

分别存在。

这样先统一上层 Checkout，而不是强行统一 Stripe 控件。


```text

     ▼
```



# 47. 最终工程原则

整个支付体系建议固定以下 10 条：

1. **Server 决定多少钱。**
2. **PSP 决定钱是否真的收到了。**
3. **Payment Domain 解释 PSP 结果。**
4. **Webhook 不能直接改订单。**
5. **订单完成只走统一业务入口。**
6. **所有支付创建必须幂等。**
7. **所有 Webhook 必须可去重、可追踪、可重试。**
8. **PSP ID 不是内部业务 ID。**
9. **Checkout UI 与 PSP UI 分层。**
10. **Stripe-first，但业务架构不绑定 Stripe。**
