> 依据：《支付系统优化.md》（P0 TECH BASELINE V1.0）
> 性质：**纯只读分析**，未修改任何代码。基于 6 层跨层代码检索 + 领域 Skill（`ai/skills/pallastrade-payments/SKILL.md`）+ 仓库 research/design 文档交叉验证。

## 0. 一句话结论（先读这段）

**《支付系统优化.md》描述的现状假设（"Order/Checkout/Admin 直接依赖 Stripe SDK、存 `stripe_payment_intent_id` 列、Webhook 直改订单"）与本仓库实际现状并不一致。**

PallasTrade 已经走过一轮支付抽象（`PaymentMethod/Gateway` 多态 + `PaymentSession` 5.4+ 会话抽象 + Webhook 收敛 + Stripe SDK 全锁在 `pallastrade_stripe` gem 内）。因此 P0 的真实差距**不是「从零建 Payment Domain」**，而是：

1. **无显式 `PaymentProvider` 接口 + `ProviderRegistry`**——`PaymentMethod`（配置实体，存凭据）同时兼任了「provider 行为」角色，概念混合；
2. **无 `PaymentAttempt` 模型**——`PaymentSession` 承担了近似 attempt 的职责，但 `Payment ↔ PaymentSession` 是 **1:1 硬拼接**（`payment.response_code ↔ session.external_id`），不支撑未来「Stripe 失败 → Adyen 重试」的 1:N 建模；
3. **Webhook 事件不落库**——无 `payment_webhook_events` 表，幂等靠「会话终态 + 30s 延迟 Job + 限流」实现，无「provider_event_id 唯一约束」级去重；
4. **状态/错误/金额语义未统一到"内部规范"**——Payment 状态机沿用传统 `checkout/pending/completed/void`（贴近 Solidus 命名），错误处理仅 `GatewayError` 粗粒度，金额 DB 层是 `decimal(10,2)` 主单位而非 minor-unit integer；
5. **凭据明文存储**——Gateway `preferences` 明文 text 列（无 AR 加密），与 P0 安全要求冲突；
6. **术语命名冲突需先对齐**——文档的 `PaymentMethod`（= CARD/APPLE_PAY…）与代码的 `PaymentMethod`（= Stripe/StoreCredit 配置）**同名不同义**，落地前必须建立术语映射（见 §4）。

其余（跨域禁止、Webhook 不直改 Order、Idempotency 基础、Trace/事件机制、文档纪律）在现有代码中**已有较好的雏形**，P0 应"补齐 + 显式契约化"，而非推倒重来。

## 1. CURRENT_PAYMENT_ARCHITECTURE（现状架构）

### 1.1 分层与代码归属

支付代码**几乎全部在 framework gems**（Host App `backend/app/` 对 Stripe 耦合 = 0）：

| 层 | 位置 | 角色 |
| --- | --- | --- |
| Host App | `backend/app/` | 仅 2 个模型（`User`/`AdminUser`）+ initializer 配置 + Gemfile 声明 gateway gems；**无支付 controller/service/model** |
| Core | `backend/pallastrade_gems/pallastrade_core/` | 支付领域模型 + 状态机 + 服务（`Payment`/`PaymentMethod`/`PaymentSession`/`Refund`/`Order`/`Carts::Complete`…） |
| API | `backend/pallastrade_gems/pallastrade_api/` | v3 REST 端点 + Webhook 入口 + 序列化 + 错误处理 |
| Admin | `backend/pallastrade_gems/pallastrade_admin/` | Rails 后台 UI（orders/payments/refunds/payment_methods 资源控制器） |
| Stripe | `backend/pallastrade_gems/pallastrade_stripe/` | **唯一直接调用 Stripe SDK 的层**（Gateway + 3 个 concern + services/presenters） |
| Adyen / PayPal | `pallastrade_adyen` / `pallastrade_paypal_checkout` | 平级 provider gem（当前非主力） |
| Storefront | `storefront/src/` | Next.js 商城（`@pallastrade/sdk` + Stripe.js 前端） |
| SDK | `platform/packages/sdk/` | `@pallastrade/sdk` Store 客户端（cart/order 双域 payment_sessions 等） |

> 注：`platform/packages/` 实际只含 `cli` / `create-pallastrade-app` / `docs` / `sdk` / `sdk-core`；**`admin-sdk`、`dashboard`、`dashboard-ui`、`dashboard-core` 源码不在本 checkout**（与 AGENTS.md 描述结构不符）。Admin 管理界面当前是 Rails 版 `pallastrade_admin`。

### 1.2 核心领域调用链（当前）

```text
Storefront (Next.js)
   |  @pallastrade/sdk（服务端 data layer）／ 同源 BFF /api/checkout/start（新统一流程）
   v
pallastrade_api  v3
   |- POST /carts/{id}/submit            -> Carts::Submit（建 or_ Order, state=pending）
   |- POST /orders/{oid}/payment_sessions -> PaymentSessions::Start
   |- PATCH .../payment_sessions/{sid}/complete -> complete_payment_session -> Carts::Complete
   `- POST /api/v3/webhooks/payments/{pm_id}   -> 同步验签 -> HandleWebhookJob(30s)
        v
pallastrade_core
   |- PaymentSessions::Start   （Order 锁 + operation_key 幂等 + 会话复用）
   |- PaymentMethod 虚拟 API    （payment_session_class / create/update/complete_payment_session / parse_webhook_event）
   |- Carts::Complete          （pay! + finalize!，唯一订单完成入口，幂等）
   |- Payments::HandleWebhook  （:captured/:authorized -> confirm! -> Carts::Complete）
   `- Payment / PaymentSession / Refund 状态机
        v
pallastrade_stripe  （Stripe SDK 唯一持有者）
   |- PallasTradeStripe::Gateway（api_key/send_request/protect_from_error）
   |- Gateway::PaymentIntents / PaymentSessions / PaymentSetupSessions / Tax
   |- PaymentSessions::Stripe（STI；external_id=cs_ 或 pi_；external_data.client_secret）
   `- WEBHOOK_EVENT_ACTIONS（Stripe event -> :captured/:authorized/:failed/:canceled 归一）
        v
Stripe
```

### 1.3 数据模型（核心表）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `pallastrade_orders` | `payment_state`(string)、`payment_total`(decimal 10,2)、`state`、`status`(draft/placed/canceled)、`total`、`payment_combination_id`、`split_from_id/parent_id` | 订单 |
| `pallastrade_payments` | `amount`(decimal 10,2)、`state`(状态机)、`number`(唯一)、**`response_code`(= Stripe pi_/cs_)**、`order_id`(可空,P4)、`payment_combination_id`、`source_id/type`(多态)、`cvv/avs_response` | **Payment**：一次扣款记录 |
| `pallastrade_payment_sessions` | **`external_id`**(NOT NULL, cs_/pi_)、`external_data`(jsonb: client_secret/operation_key/mode)、`status`(状态机)、`type`(STI)、`amount`、`order_id`、`payment_method_id`、`payment_combination_id` | **会话**（≈ attempt 雏形） |
| `pallastrade_payment_setup_sessions` | `external_id`/`external_client_secret`/`external_data`、`status`、`type` | 钱包存卡会话 |
| `pallastrade_payment_sources` | `type`(STI)、`gateway_payment_profile_id`、`gateway_customer_profile_id` | 多态支付源 |
| `pallastrade_payment_methods` | `type`(STI, 含 `PallasTradeStripe::Gateway`)、**`preferences`(text, 明文存 sk/pk)**、`auto_capture`、`active`、`display_on` | 支付方式配置 |
| `pallastrade_stripe_payment_intents` | `stripe_id`、`client_secret`、`ephemeral_key_secret`、`customer_id`… | **旧/旁路表**（当前主链路已迁 PaymentSession） |
| `pallastrade_stripe_webhook_keys` | `signing_secret`、`stripe_id` | webhook 签名密钥（每 gateway） |
| `pallastrade_payment_combinations` / `payment_splits` / `payment_capture_events` | 状态机 + 分摊金额字段 | P4/P5 组合支付载体（能力层默认关闭） |
| `pallastrade_refunds` / `reimbursements` / `gateway_customers` 等 | — | 退款/报销/网关客户 |

**关键关联事实**：
- `Payment ↔ PaymentSession` 靠 **`Payment.response_code` ↔ `PaymentSession.external_id`** 字符串拼接 1:1（**无正式 FK**）；
- Payment 状态机：`checkout -> processing -> pending -> completed | failed | void | invalid`（事件 `started_processing/pend/complete/failure/void/invalidate`）；
- PaymentSession 状态机：`pending/processing -> completed | failed | canceled | expired`；
- Order `payment_state` 由 `OrderUpdater` 派生（paid/balance_due/credit_owed/void/failed），非独立状态机。

### 1.4 ID 体系与金额

- **ID**：`PallasTrade::PrefixedId`（`has_prefix_id`）+ **Sqids**（min_length:10）编码整数主键，运行时计算、无 DB 列。前缀：`or_`(Order)、`py_`(Payment)、`pm_`(PaymentMethod)、`ps_`(PaymentSession/PaymentSource)、`pss_`、`re_`(Refund)、`card_`、`pcom_`、`psplit_`、`pce_`、`gcus_`；另有可读号 `P#/R#`（NumberGenerator）。
  → 文档建议 prefix+ULID，但文档亦言「已有成熟 ID 生成器则优先兼容」——**现状 Sqids 体系即属成熟体系，P0 应兼容而非改 ULID**。
- **金额**：DB 全部 `decimal(10,2)` **主单位**；`PallasTrade::Money`（包 Monetize）在**网关边界**才转 minor unit（cents）。与文档「DB 层 integer minor-unit」不一致（全量迁移代价大，需权衡）。

### 1.5 主要服务入口

| 服务 | 位置 | 职责 |
| --- | --- | --- |
| `PallasTrade::PaymentSessions::Start` | core | 幂等启动支付会话；Order 锁 + 复用 active 会话 + `operation_key`（attempt-N 计数）稳定幂等键；provider I/O 在锁事务外 |
| `PallasTrade::Carts::Submit` | core | Cart → Order（`state=pending`） |
| `PallasTrade::Carts::Complete` | core | **唯一订单完成入口**：`pay! + finalize!`，幂等（`completed?` 短路 + `pay! unless paid`） |
| `PallasTrade::Payments::HandleWebhook` | core | 消费归一 action：captured/authorized→confirm!+Complete；failed/canceled→会话终态 |
| `PallasTrade::Payments::PaymentCombinations::{Create,Complete}` | core | 组合支付闭环（P4，无端点） |
| `PallasTradeStripe::Gateway`（+concern） | stripe | 唯一 Stripe SDK 接触面：`send_request`/`protect_from_error`/幂等键 |

## 2. PAYMENT_COUPLING_ANALYSIS（耦合分析）

### 2.1 Stripe SDK 使用点（全仓唯一持有者 = pallastrade_stripe）

| 文件 | 关键 Stripe 调用 |
| --- | --- |
| `app/models/pallastrade_stripe/gateway.rb` | `Stripe::Refund.create/list`、`Customer.create/update`、`Charge.retrieve`、`EphemeralKey.create`、`SetupIntent.create`、`PaymentMethod.attach`、`Webhook.construct_event`、`Tax::Calculation`；`api_options { api_key }` + `send_request` |
| `.../gateway/payment_intents.rb` | `PaymentIntent.create/update/retrieve/confirm/capture` |
| `.../gateway/payment_sessions.rb` | `Checkout::Session.create/retrieve/list` |
| `.../gateway/payment_setup_sessions.rb` | `SetupIntent.retrieve` |
| services：`create_gateway_webhooks.rb`、`register_domain.rb`、`webhook_handlers/*` | `WebhookEndpoint.*`、`PaymentMethodDomain.*`、`Checkout::Session.list`… |
| controllers：`apple_pay_domain_verification`、`confirm_payments`、`stripe_event/webhook_controller_decorator` | 验签/ApplePay/confirm |

**结论**：core/api/admin/storefront 对 `Stripe::*` **零直接引用**——SDK 隔离在「Stripe gem = adapter」这一层已基本成立，比 P0 文档假设的好。

### 2.2 残留耦合点（重构注意）

1. **`PaymentSessions::Stripe`（STI 领域模型）携带 Stripe 语义方法**：`stripe_id/stripe_payment_intent/stripe_charge/checkout_session_payment_status/payment_intent_mode?`——领域模型渗透 gateway 细节；
2. **webhook 事件→action 归一表 `WEBHOOK_EVENT_ACTIONS` 由 Stripe gem 定义、在 api controller 内同步解析**，core 只消费归一后 action——归一逻辑的"所有权"在 provider 层，尚可，但未落库；
3. **`Payment.response_code` 直接存 Stripe `pi_`/`cs_`**（无独立 `provider_payment_id` 概念封装）；
4. 旧 `pallastrade_stripe_payment_intents` 表 + `CreatePaymentIntent` 模式与新版 PaymentSession 双轨并存；
5. **Legacy `Payment::Processing`（authorize/purchase/confirm/capture）与 2026-08 PaymentSession/Checkout Session 流程并存**；Order 侧 legacy `checkout` 状态机（cart→…→complete）与标准流程（pending→paid→…）双轨由 `standard_flow?` 隔离；
6. **错误处理只有 `Stripe::StripeError → PallasTrade::Core::GatewayError` 粗粒度翻译**，无 decline-code 级处理（全仓未找到 `card_declined`/`Stripe::CardError` 分支）；
7. **Gateway secret 明文存 `preferences` text 列**（无 AR 加密；skill 亦明确警告）；
8. Storefront 侧：**自绘卡表单（CardPaymentForm, `confirmCardPayment`）与 PaymentElement（StripePaymentForm, `checkout.confirm`）两套 Stripe UI 并存**，无统一门面；cart 域 / order 域两套 payment_sessions 端点并存；client_secret `%2F` 解码约定散落多处。

### 2.3 跨层六层检索结论

| 层 | 检索结论 |
| --- | --- |
| backend/app（App） | **无支付代码**（耦合 0）；仅 initializer 配置队列/flag |
| core | 领域核心（模型/状态机/服务），对 Stripe 零引用，依赖 `PaymentMethod` 虚拟 API 与 `GatewayError` |
| api | v3 端点 + webhook 入口，网关无关，消费归一 action |
| admin | 资源控制器 UI（orders/payments/refunds/payment_methods），网关无关 |
| storefront | Stripe.js 前端三能力并存（见 §5），SDK/BFF 封装后端契约 |
| platform | `@pallastrade/sdk` 支付方法完整；admin-sdk/dashboard 源码不在本 checkout |

## 3. 术语映射：文档概念 ↔ 代码现状（P0 落地第一件事）

《支付系统优化.md》是通用蓝图，术语与 PallasTrade 现状**并非一一对应**，直接套用会踩坑：

| P0 文档概念 | 含义（文档） | PallasTrade 现状对应物 | 差异/风险 |
| --- | --- | --- | --- |
| `Payment` | 「业务需收多少钱」聚合 | `PallasTrade::Payment` | 现有 Payment 更像「一次扣款记录」+`order_id` 绑定；组合支付后 `order_id` 可空已出现 |
| `PaymentAttempt` | 一次 PSP 尝试，1:N | **无该模型**；近似 = `PaymentSession`（每次起会话 attempt-N） | Session 与 Payment 1:1；无 fallback/重试建模 |
| `PaymentMethod` | CARD/APPLE_PAY/PAYPAL… | `PallasTrade::PaymentMethod` = Stripe/StoreCredit/Check 配置（STI） | **同名不同义，最危险**；卡类型在代码里是 `CreditCard`/`PaymentSource`/wallet |
| `PaymentProvider` | STRIPE/ADYEN 抽象 | `PallasTrade::Gateway`（delegate authorize/capture/…）+ PaymentMethod 虚拟 API | 无显式 Provider 接口 + Registry；`PaymentMethod` 配置与行为混合 |
| `StripePaymentProvider` | Stripe adapter | `PallasTradeStripe::Gateway` + concerns + presenters | 已存在（≈ 目标形态），但语义方法散布在 STI 模型 |
| `PaymentStatus`（SUCCEEDED…） | 统一内部状态 | Payment `checkout/pending/completed/void/failed/invalid` + Session `pending/processing/completed/failed/canceled/expired` + Order `payment_state` | **三套状态并存**，与文档单一枚举体系冲突 |
| `FailureCode`（DECLINED…） | 统一错误码 | 仅 `PallasTrade::Core::GatewayError` + api `ERROR_CODES`（payment_failed/gateway_error/idempotency_key_reused） | 无 decline-code 级内部码 |
| `Money`（minor-unit） | integer 最小单位 | DB `decimal(10,2)`；网关边界转 cents | 存储语义不一致 |
| `payment_webhook_events` | webhook 落库去重 | **不存在** | 幂等靠会话终态 + Job |
| `idempotency_records` | 通用幂等表 | 无通用表；靠 `operation_key`/会话复用 + HTTP `Idempotency-Key` concern（支付会话 create **未挂**此 concern） | 逻辑幂等已不错，缺通用记录表 |
| `PaymentStateMachine` | 集中迁移规则 | 模型内 `state_machine` + `processing.rb` | 已集中，但三域（Payment/Session/Order）各自为政 |
| Trace/Request ID | 全链路贯穿 | api `error_handler` 有 `request_id`；`PallasTrade::Events`（ActiveSupport::Notifications）+ Subscriber 基类 | 支付链路日志字段化检索未系统化 |

按《支付系统优化.md》P0 建设清单逐项对照：

| P0 能力（文档） | 现状 | 差距等级 | P0 建议动作 |
| --- | --- | --- | --- |

## 5. 前端（Storefront）支付现状要点

- **三套 Stripe 前端能力并存**：
  1. 经典 Elements 三字段自绘卡（`CardPaymentForm.tsx`，`confirmCardPayment(pi_secret)`）——**新标准流程**，规避 CN 网络 PaymentElement 懒加载卡死（PRD-20260831）；
  2. `CheckoutProvider + PaymentElement`（`StripePaymentForm.tsx`，`checkout.confirm`）——legacy cart 流程 / 合并支付 / 账户补付；
  3. `ExpressCheckoutElement`（Apple/Google Pay，`confirmPayment`）。
- **无 `redirectToCheckout`/Hosted Checkout**——全部嵌入式。
- **API 调用纪律良好**：浏览器不接触 secret；服务端 data layer 全走 `@pallastrade/sdk`；唯一裸 fetch = 同源 BFF `/api/checkout/start`（新统一流程，规避 RSC refresh 竞态）。
- **金额信任链**：展示用后端预格式化 `display_*`；但 Stripe 金额/lineItems 由前端 `toCents/buildLineItems` 重算——前后端口径需同步。
- **结果判定**：客户端乐观跳转 + `payment-result/[id]` 服务端权威终态（前端不信任 `confirmPayment` 返回值）。

## 11. 五项深挖结论（2026-09-02，代码级验证）

> 以下 5 项均基于**只读精读源码**得出（给出文件与方法定位，便于复核）。凡涉及「疑点/需验证」处已明确标注。

### 11.1 Q1：PaymentSession 与 Payment 的真实创建 / 关联 / 完成生命周期

#### 创建 PaymentSession（起会话）

**入口**（标准流程主入口）：
`POST /api/v3/store/orders/:order_id/payment_sessions`
→ `pallastrade_api/app/controllers/.../store/orders/payment_sessions_controller.rb#create`
→ `PallasTrade::PaymentSessions::Start.call(order:, payment_method:, external_data:)`（core）

**`PaymentSessions::Start` 核心逻辑**（`core/app/services/pallastrade/payment_sessions/start.rb`）：

1. `order.with_lock` 内：
   - `amount = order.amount_due`（`order.rb#amount_due` = `[outstanding_balance - total_applied_store_credit, 0].max`）——**金额一律服务端从 Order 派生，不信任前端传值**；
   - 校验 `amount > 0`、`payment_method_available?`；
   - `reusable_session`：复用「同 method + 同 amount + 同 mode」且 status ∈ pending/processing 的 active 会话（幂等/防重复点 #1）；
   - 无复用则返回 `[amount, operation_key]`，**在锁外**调用 provider（避免持锁等网络）；
2. `operation_key = "pallastrade-order-#{id}-method-#{pm}-#{mode}-attempt-N"`（N = 终端会话数 +1）→ 作为 Stripe 幂等键（幂等点 #2）；
3. 锁外 `payment_method.create_payment_session(order:, amount:, external_data.merge(idempotency_key: operation_key))`；
4. 二次 `order.with_lock` 收敛并发：若他人已建 winner → cancel 本会话返回 winner；`RecordNotUnique` 兜底重查（幂等点 #3）。

**Stripe 侧实现**（`stripe/.../gateway/payment_sessions.rb`）两种模式：
- **Checkout Session 模式（默认）**：`amount_in_cents = PallasTrade::Money.new(total, order.currency).cents`（total = 传入 amount 或 `order.total_minus_store_credits`）→ `CheckoutSessionPresenter`（单条 `line_item.unit_amount = amount_in_cents`，`mode: payment, ui_mode: elements`）→ `Stripe::Checkout::Session.create(payload, {api_key, idempotency_key})` → 落库 session：`external_id = cs_xxx`、`external_data = {client_secret, operation_key}`；
- **PaymentIntent 模式（自绘卡，`external_data.mode = 'payment_intent'`）**：`Stripe::PaymentIntent.create` → 落库 `external_id = pi_xxx`、`external_data = {client_secret: pi_xxx_secret, mode: 'payment_intent'}`。

#### Payment 的创建（不在起会话时，而在"完成/确认"时）

Payment 记录**不是**在 `Start` 时创建，而是在支付被确认的路径里经 `PaymentSession#find_or_create_payment!` 惰性创建：

- 基类（`core/.../payment_session.rb#find_or_create_payment!`）：`order.payments.find_or_create_by!(payment_method:, response_code: external_id)`（假设 response_code==external_id）；
- **Stripe 覆写**（`stripe/.../payment_sessions/stripe.rb#find_or_create_payment!`）→ `PallasTradeStripe::CreatePayment`（`stripe/.../services/create_payment.rb`）：
  - `response_code: payment_intent.stripe_payment_intent&.id || payment_intent.stripe_id`；
  - ⚠️ **关键**：2026-08-31 bugfix 注释明确——`Payment#response_code` **必须存底层 `pi_` PaymentIntent id**（`Gateway#handle_authorize_or_purchase`/`credit` 都以 response_code 作为 PaymentIntent id 调 Stripe，若存 `cs_` 会报 `No such payment_intent`）；
  - 由 `CreateSource` 从 Stripe charge 建多态 source；`find_or_initialize_by(payment_method_id + response_code + amount)` 防 job 重试重复建 Payment。

#### Payment ↔ PaymentSession 的关联（⚠️ 核心发现/疑点）

模型上双向 has_one（均无正式 FK，靠字符串拼接）：

```ruby
# PaymentSession
has_one :payment, foreign_key: :response_code, primary_key: :external_id
# Payment
has_one :payment_session, foreign_key: :external_id, primary_key: :response_code
```

- **pi_ 模式**：`external_id = pi_xxx` 且 `Payment.response_code = pi_xxx` → 拼接成立 ✅；
- **cs_ 模式**：`external_id = cs_xxx`（Checkout Session id），而 `Payment.response_code = pi_xxx`（CreatePayment 强制取 PI id）→ **has_one 拼接断裂**（`cs_ ≠ pi_`）❌。

影响面（代码证据）：
- `complete_payment_session`（gateway/payment_sessions.rb）里 `payment = payment_session.payment` 在 cs_ 模式下可能取到 nil → 依赖 has_one 拿 payment 的**直接链路可能失效**（但 `find_or_create_payment!` 返回值与 `order.payments` 兜底仍可定位）；
- `PaymentSessionSerializer`（api）`one :payment, if: session.payment.present?` → cs_ 模式下序列化可能不带 payment；
- Payment 上 `has_one :payment_session`（response_code→external_id）在 cs_ 模式同样 miss。

> ⚠️ **标注为需验证风险点**：cs_（PaymentElement/Checkout Session 迁移后默认形态）下 session↔payment 的 has_one 1:1 契约是否仍成立，需用真实 cs_ 完成数据验证（`PaymentSession.find(cs_session).payment` 是否为 nil）。若断裂成立，说明当前「Session 已完成但 Payment 关联查不到」的兼容依赖 `order.payments` 定位，P0 引入 PaymentAttempt 时必须先修复该关联（如新增正式 FK/索引或统一 external_id 语义）。

#### 完成生命周期（三路收敛，均幂等）

**完成路径 A：前端 active confirm 后调 API complete**
`PATCH /orders/:order_id/payment_sessions/:id/complete`（orders/payment_sessions_controller.rb#complete，`with_order_lock` 内）：
1. 已 `completed?` → 直接返回（幂等）；
2. 组合支付 → `PaymentCombinations::Complete`；
3. `payment_method.complete_payment_session`：
   - Stripe 实现：取 PI（pi_ 直取 / cs_ 经 `retrieve_checkout_session(...expand payment_intent)`）→ **`verify_payment_intent_matches!(pi, session.amount_in_cents, currency)` 金额/币种强校验** → `payment_intent_accepted?` → `session.process`（可转才转）→ `find_or_create_payment!` → 依 PI 状态 `payment.process!`（auto_capture→purchase!/否则 authorize!）→ `session.complete`；不接受则 `session.fail`；
   - **注意：complete_payment_session 不完成订单**（注释明示）；
4. controller 随后：`unless @order.completed? → carts_complete_service(Carts::Complete).call(cart: @order)`（standard 分支：`complete_standard_order!` = `process_payments!`（若需）→ `order.pay! unless paid` → `order.finalize!` → 库存/拆单；**Carts::Complete 幂等**）。

**完成路径 B：Stripe Webhook（异步兜底，30s 延迟）**
`POST /api/v3/webhooks/payments/:pm_id`（api webhooks/payments_controller.rb#create）：同步验签（非法 401）→ 合法则 `HandleWebhookJob.set(wait: 30s)` 立即 200 → Job（`core/app/jobs/.../handle_webhook_job.rb`）→ `Payments::HandleWebhook`：
- `:captured/:authorized` → `handle_success`：`order.with_lock` 内 → **`session.reload.completed?` 短路（幂等，若 API complete 已赢则跳过）** → `find_or_create_payment!` → `payment.confirm!`（auto_capture→complete!+capture_event / 否则 pend!）→ `session.complete` → 未完成则 `Carts::Complete`；
- `:failed/:canceled` → `session.fail/cancel`（can_* 守卫）。

**完成路径 C：Rails 版 redirect 兜底**
`GET /stripe/confirm_payment/:id?session=`（stripe confirm_payments_controller.rb#show）：先判 canceled/completed → `complete_payment_session` → 完成后 `Carts::Complete` → redirect 完成页。幂等（已 completed 视为成功）。

**Payment/PaymentSession/Order 三态机**（真实事件）：
- Payment：`checkout → processing(pend 前) → pending | completed | failed | void | invalid`；`after_transition` 写 `state_changes`；
- PaymentSession：`pending → processing → completed | failed | canceled | expired`（`expired?` 由 `expires_at` 判定）；
- Order：`pending → paid（pay!）→ …→ finalize!（status='placed'）`；`payment_state` 由 `OrderUpdater` 派生。

### 11.3 Q3：前端金额 → PaymentSession → Stripe amount 的完整信任链

#### 信任链总览（核心结论：金额权威在后端 Order）

```text
Order（服务端权威）
  |- total / amount_due / total_minus_store_credits   <- decimal(10,2) 主单位
  |- PaymentSessions::Start: amount = order.amount_due （不接受前端 amount）
  |- Stripe create: cents = Money.new(total, currency).cents
  |      -> CheckoutSessionPresenter line_items[0].unit_amount = cents（单条聚合行）
  |      -> PaymentIntent.amount = cents（pi_ 模式）
  `- complete: verify_payment_intent_matches!(pi.amount==session.amount_in_cents, currency)
       ^ 最终防线：后端用自己落库的 session.amount 校验 Stripe 实收
前端（仅展示 + Stripe UI 本地显示）
  |- 展示金额：后端 display_* 预格式化字符串（零本地小数运算）
  |- Stripe Elements/PaymentElement：消费后端 client_secret，行项目由后端 Presenter 构造
  `- Express：本地 buildLineItems/toCents 重算 Elements 显示（见 11.3.3 风险）
```

#### 关键转换点

1. **Order 金额**：`orders.total / payment_total / amount_due` 等全部 `decimal(10,2)` 主单位（`money_methods` + `OrderUpdater` 汇总）；
2. **会话金额**：`PaymentSession.amount = order.amount_due`（Start）或 `order.total_minus_store_credits`（gateway 未传 amount 时）；`session.amount_in_cents = PallasTrade::Money.new(amount, currency).cents`；
3. **PallasTrade::Money**（`core/lib/pallastrade/money.rb`，包 Monetize）：`initialize` 用 `Monetize.parse`（可解析 `"129.99"`/129.99）；`cents` 委托 money gem 按 `subunit_to_unit` 换分；`amount_in_cents = (cents/subunit_to_unit*100).round`（兼容零小数币种写法，但**实际送 Stripe 用 `.cents`**）；
4. **Stripe 侧**：`CheckoutSessionPresenter` 单条 `line_item`（quantity:1, unit_amount=cents, product_data.name=order.number）；`payment_intent_data` 带 `transfer_group: order.number` + metadata `pallastrade_order_id`；客户已存在时仅传 `customer`，游客补 `customer_email`（两者互斥 bugfix）；
5. **完成后端防线**：`verify_payment_intent_matches!(pi, expected_amount=session.amount_in_cents, expected_currency=session.currency)`——不匹配抛 `GatewayError`，**防止 Stripe 实收与本地订单金额不一致仍被记录为成功**。

#### 前端 Express 的金额风险点（口径需同步）

- `storefront/src/lib/utils/express-checkout.ts`：`toCents(amount, currency)` 本地 `×100`（零小数币种表 `STRIPE_ZERO_DECIMAL_CURRENCIES` 原样返回）；`buildLineItems` 从 `order.item_total/discount_total/additional_tax_total` **前端重算**子total/折扣/税；
- Express 的 Elements amount/行项目是前端算的，但**后端会话金额仍是 order.amount_due（服务端权威）**——若后端金额语义（含/不含税、优惠口径、运费是否计入）与前端 `toCents/buildLineItems` 口径不一致，会出现 Elements 显示金额 ≠ Stripe 实收校验金额（Stripe 会以 `unit_amount` 聚合行与 Elements 校验，前端行项目仅展示；后端最终以 `verify_payment_intent_matches!` 兜底）；
- 注释提示 shipping 不应计入 line_items（Express shippingRates 单独处理），否则触发 IntegrationError。
- ⚠️ 结论：**任何后端金额语义变更（税/折扣/运费计入规则）必须同步前端 `toCents/buildLineItems` 与 Express shippingRates**，这是 P0 金额规范统一（minor-unit）时的高风险联动点。

### 11.4 Q4：preferences secret 当前读写 / 序列化 / 初始化机制

#### 声明与类型

`stripe/.../gateway.rb`（继承链 `PallasTrade::PaymentMethod < PallasTrade::Base`）：

```ruby
preference :publishable_key, :password
preference :secret_key, :password
```

- `preference` DSL 由 `PallasTrade::Preferences::PreferableClassMethods`（`core/lib/.../preferences/preferable_class_methods.rb`）生成 `preferred_secret_key` / `preferred_secret_key=` / `preferred_secret_key_default` 等访问器；
- `:password` 类型在 `convert_preference_value` 中**仅 `value.to_s`，无加密**（`preferable.rb`）——类型标记只用于「序列化时掩码」与「写回保护」，不落加密。

#### 存储

- 列：`pallastrade_payment_methods.preferences`（schema.rb：`t.text "preferences"`）；
- 序列化：`PallasTrade::Base` include `Preferable` → `serialize :preferences, type: Hash, coder: YAML`（preferable.rb）——**YAML 明文文本列**；
- `after_initialize`（base.rb）：`self.preferences = default_preferences.merge(preferences)`（默认值并入）；
- ⚠️ **无 AR 加密**（`pallastrade_payment_methods` 的 preferences 未套 `encrypts`；Host App 的 active_record_encryption initializer 仅用于 AI secrets）。**DB dump/备份 = 明文含 sk/pk**（skill 明确警告，与本分析 §9-5 一致）。

#### 读取

- 运行时：`api_options { api_key: preferred_secret_key }` → `send_request(opts)`（所有 Stripe 调用带 `{api_key: ..., idempotency_key: ...}`）；
- 校验：`validate_secret_key`（gateway.rb，`unless test?`）：`Stripe::Refund.list(limit:0, api_options)`——`AuthenticationError`→"Secret key is invalid"；`PermissionError(secret_key_required)`→"提供了 publishable key"；启动即真实请求 Stripe 验证；
- webhook 签名密钥：独立表 `pallastrade_stripe_webhook_keys.signing_secret`（经 `payment_methods_webhook_keys` 中间表多对多）+ `ENV['STRIPE_SIGNING_SECRET']` 兜底（`webhook_signing_secrets`）。

#### 序列化（对外/Admin 展示）

- `PallasTrade::PreferenceSchema` + `Preferences::Masking`（`core/lib/.../preferences/masking.rb`）：
  - `serialized_preferences`（Admin PaymentMethodSerializer 的 `preferences` 属性）= 遍历 schema，`:password` 字段 → `mask(value) = "••••" + 后4位`；
  - `serialized_preference_schema` = 字段清单（key/type/default），`:password` 的 default 被置 nil（防泄露）；
  - 即 **API 返回永远不出现完整 secret**，只给掩码；非 password 字段原样。

#### 写入（Admin API / 掩码回写保护）

- Admin v3：`admin/payment_methods_controller.rb`（STI via `SubclassedResource` concern）：permit `preferences: {}` → `apply_preferences` 逐个 `resource.set_preference(key, value)`（走 typed setter 转换）；**未知 preference key 静默丢弃**；
- **掩码回写保护**（`subclassed_resource.rb#apply_preferences`）：`password_keys` 命中且 `Masking.masked?(value)`（即前端把 `••••abcd` 原样传回）→ **跳过不覆盖**，保留库中真值——这是防「拿到掩码再保存 → secret 变掩码」的关键守卫；
- 前端 Admin UI 依赖 schema 端点渲染字段（掩码值不回显真值）。

#### 初始化（首次配置）

- 无「启动时从 ENV 自动落库」逻辑；真实 store 在 **Admin 设置页（Settings → Payments）** 录入 sk/pk → POST 存入 `preferences`；webhook signing secret 在创建 webhook endpoint 时由 `CreateGatewayWebhooks` 服务存 `webhook_keys` 表（也可手动填 ENV `STRIPE_SIGNING_SECRET`）；
- spec/factory 用 `ENV['STRIPE_SECRET_KEY']`/`STRIPE_PUBLISHABLE_KEY`（`spec/support/stripe_helper.rb`）；
- ⚠️ P0 差距：文档要求「DB 只存 secret_reference + KMS/Vault」；现状为**明文 text 列 + 掩码展示 + 回写保护**（传输/展示安全 OK，静态存储不安全）。

### 11.5 Q5：Stripe webhook 的重复 / 乱序 / 重试实际处理路径

#### 入口与验签（同步、失败即 401）

`POST /api/v3/webhooks/payments/:payment_method_id`（`api/.../webhooks/payments_controller.rb#create`）：
- 限流 120/min/IP（429 + Retry-After 60）；
- 同步 `payment_method.parse_webhook_event(raw_post, headers)`：
  - `Gateway#verify_webhook_signature`：遍历 `webhook_signing_secrets`（表内各 key + ENV 兜底）逐个 `Stripe::Webhook.construct_event`，全失败 → `WebhookSignatureError` → **401**；
  - 事件→action：`WEBHOOK_EVENT_ACTIONS`（`payment_intent.succeeded/amount_capturable_updated/payment_failed` + `checkout.session.completed/async_payment_succeeded/async_payment_failed/expired` → `:captured/:authorized/:failed/:canceled`）；
  - session 解析：event object id `cs_` → 按 external_id 直查；`pi_` → 直查 external_id=pi_ **或** Stripe `Checkout::Session.list(payment_intent: pi_)` 反查 cs_ session（`find_session_by_payment_intent`）；解析不到 → 返回 nil（controller `head :ok` 吞掉）；
- 合法事件：`HandleWebhookJob.set(wait: 30s)` **延迟 30 秒**再处理，controller 立即 200——延迟目的是「让 storefront 自己的 complete 先落地」，避免 webhook 与 API complete 竞争双处理（见 base.rb webhook_handlers 注释同思路：legacy 用 10s）。

#### 重复投递（Duplicate）处理

**无 `payment_webhook_events` 落库表、无 `(provider, provider_event_id)` 唯一约束**——去重完全靠**业务幂等链**：
1. `HandleWebhook#handle_success`：`order.with_lock` → `payment_session.reload.completed?` **短路**（若 API complete 或上一 webhook 已完成会话 → 直接 return，不重复建 payment/不重复完成订单）；
2. `find_or_create_payment!` → `CreatePayment` 用 `find_or_initialize_by(payment_method+response_code+amount)`（防 job 重试重复建 Payment 记录）；
3. `payment.confirm!`（内部 `completed?` 已判）→ `session.complete if can_complete?`（状态机守卫，已 completed 不再转移）；
4. `Carts::Complete` 幂等（`completed?` 短路 + `pay! unless paid` + `finalize!`）。
→ 结论：**重复 webhook 不会重复扣款/重复完成订单**，靠「会话终态 + Order/状态机守卫」而非「事件落库去重」。

#### 乱序（Out-of-order）处理

| 乱序场景 | 实际路径 |
| --- | --- |
| webhook 先到、API complete 后到 | webhook 30s 延迟给 complete 让路；若 webhook 真先完成 → 会话 completed，API complete 端点 `completed?` 短路直接返回 |
| API complete 先到、webhook 后到 | webhook Job 处理时 `session.completed?` 短路，跳过 |
| `checkout.session.completed` 与 `payment_intent.succeeded` 重复发同义事件 | 都归一 `:captured`，走同一幂等链（先到者完成，后到者短路） |
| `amount_capturable_updated`(:authorized, 手动捕获) 后 `payment_intent.succeeded`(:captured) | authorized→`confirm!`（auto_capture=false→`pend!`）→ 后续 succeeded→payment.completed? 已处理则跳过；依赖 Payment 状态机守卫 |
| failed 事件在 succeeded 后（极端异常） | `:failed`→`session.fail if can_fail?`（completed 会话不能 fail，被守卫拒绝）；`:canceled` 同理 |
| 会话已 expired 后又来事件 | `expired?` 判定 + `can_*` 状态机守卫 |

→ 结论：**乱序保护靠「状态机 can_* 守卫 + 会话/订单幂等短路」，无显式事件排序/版本控制**。`payments.version` 乐观锁不存在（P0 文档 §25 建议项尚未落地）。

#### 重试（Retry）路径

- **Stripe 侧**：webhook 超时/5xx 会重投。本端点**同步验签失败返回 401**、**找不到 session 返回 200**（已 ack，Stripe 不重试）、**业务处理全部异步**；
- **Job 层**（`HandleWebhookJob < PallasTrade::BaseJob`）：
  - BaseJob 默认：`retry_on Deadlocked/LockWaitTimeout/ConnectionNotEstablished/ConnectionFailed`（polynomially_longer, 5 次）+ `RecordNotFound`（2s, 3 次）+ discard 反序列化错；
  - HandleWebhookJob 额外 `retry_on Deadlocked/LockWaitTimeout`（5s, 3 次）；
  - **⚠️ 关键**：`HandleWebhook#handle_success` 内 `rescue StandardError` → `Rails.error.report` + 返回 failure（**不 raise**）→ Job 视为成功，**不再重试**。即「业务处理失败（除 DB 锁类）不会自动重投」，只留 Rails.error 日志；
- **Legacy 通道**（`use_legacy_webhook_handlers=true` 时 mount StripeEvent engine `/stripe`）：`WebhookHandlers::Base` 10s 延迟 → `CompleteOrderFromSessionJob`；新式默认走 v3 端点 30s 延迟 HandleWebhookJob；
- **限流**：120/min/IP，超限 429+Retry-After 60（Stripe 会按 Retry-After 重试）。

#### Q5 小结（对照 P0 文档）

| P0 文档要求 | 现状 | 差距 |
| --- | --- | --- |
| webhook 事件落库 + `(provider, provider_event_id)` 唯一约束 | ❌ 无 `payment_webhook_events` 表 | 🔴 高——重复靠业务幂等，无法审计/回放/对账原始事件 |
| 去重 | ✅ 会话终态 + 状态机守卫 + CreatePayment 幂等 | 🟢 低（当前覆盖足够） |
| 乱序防护 | 🟡 靠 can_* 守卫与幂等短路 | 中——无事件版本/排序，极端交错靠守卫兜底 |
| 重试 | 🟡 Job 层 DB 锁类重试；**业务异常不重试**（只 Rails.error） | 中——业务失败无重试/死信，排障依赖日志 |
| 30s/10s 延迟 | ✅ 让路 storefront complete | 低——双通道延迟常数不一致（v3=30s, legacy=10s） |
