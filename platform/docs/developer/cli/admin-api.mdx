The `pallastrade api` command group turns the CLI into a first-class Admin API client: generic HTTP verbs against any endpoint, schema introspection without leaving the terminal, and credentials that resolve automatically — from a local dev project to a production store profile. It works against any PallasTrade 5.5+ instance and is designed to be driven by both humans and AI coding agents.

```bash
pallastrade api get /products -q status_eq=active --sort -created_at --limit 10
pallastrade api get /orders/ord_x8k2J9aQ --expand items,payments
pallastrade api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'
pallastrade api patch /orders/ord_x8k2J9aQ/cancel
pallastrade api endpoints --resource orders
pallastrade api schema "POST /orders/{id}/refunds"
pallastrade api status
```

## Credentials

Credentials resolve through four layers — first match wins:

| Layer | How |
|---|---|
| Flags | `--base-url` / `--api-key` (and `--profile`, which selects a saved profile explicitly) |
| Environment | `PALLASTRADE_API_KEY` (+ `PALLASTRADE_BASE_URL`) — the path for CI and agents. `PALLASTRADE_BASE_URL` is optional: a bare key defaults to `http://localhost:3000`, so local dev needs only the key. Set it for a remote store. |
| Project | Inside a PallasTrade project with the dev stack running, the CLI mints a **read-only** key on first use and stores it in `.pallastrade/credentials.json` (gitignored) |
| Profile | `~/.config/pallastrade/config.json`, written by `pallastrade auth login` |

Host and key resolve **together** per source — a saved or minted key is never silently re-pointed at a host from a different layer. Only `--base-url` (or `PALLASTRADE_BASE_URL` paired with `PALLASTRADE_API_KEY`) re-points a key deliberately. So against local dev:

```bash
PALLASTRADE_API_KEY=sk_xxx pallastrade api get /products    # → http://localhost:3000
```

Zero configuration is needed for local development — the first `pallastrade api get` inside your project just works:

```bash
cd my-store
pallastrade api get /products
# No credentials found — minting a read-only API key via the dev stack...
# Saved to .pallastrade/credentials.json (scopes: read_all)
```

Auto-minted keys carry `read_all` only. Writes always require an explicitly created key:

```bash
pallastrade api-key create --type secret --scopes read_orders,write_products
```

For remote stores, create a secret key in the admin under **Settings → API Keys** and save it as a profile — the key is read from a prompt, never from a flag:

```bash
pallastrade auth login --profile prod --base-url https://store.example.com
pallastrade api get /orders --profile prod -q "status_eq=complete"
pallastrade auth status
pallastrade auth logout --profile prod
```

### Use with a sandbox

A [free sandbox](https://console.pallastrade.sh) works like any remote store. Create a secret key in the sandbox admin under **Settings → API Keys**, then save it as a profile:

```bash
pallastrade auth login --profile sandbox --base-url https://your-store.pallastrade.sh
pallastrade api get /products --profile sandbox
```

No local project or Docker needed — the CLI (`npm install -g @pallastrade/cli`) plus a sandbox is a complete environment for exploring the Admin API.

## Reading data

`-q` takes [Ransack](/api-reference/admin-api/querying) predicates as repeatable `key=value` pairs; sorting, pagination, and shaping flags pass through under the Admin API conventions:

```bash
pallastrade api get /products -q name_cont=shirt -q status_eq=active
pallastrade api get /orders --sort -created_at --page 2 --limit 50
pallastrade api get /products/prod_86Rf07xd --expand variants,variants.prices
pallastrade api get /customers --fields id,email --format table
```

`--fields` trims the response to the attributes you name (comma-separated). The resource `id` is **always returned** even if you don't list it, so you only need to name the extra fields. `--expand` is the companion axis — `--fields` selects top-level attributes, `--expand` pulls in related resources:

```bash
pallastrade api get /products --fields name,price          # → id + name + price
pallastrade api get /products --fields name --expand variants
```

### Output format

Output is JSON on stdout, and it adapts to where it goes:

- **In a terminal** — indented and syntax-colored, for reading.
- **Piped or redirected** — compact, single-line, uncolored, so it stays fast and feeds cleanly into `jq` (color codes would corrupt it).

```bash
pallastrade api get /products --limit 5 | jq '.data[].name'
```

`--format table` renders collections as a table for humans (nested objects collapse to `{…}`, arrays to `[N]`).

## Writing data

Request bodies are flat JSON (no root wrapping), inline, from a file, or from stdin:

```bash
pallastrade api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'
pallastrade api post /orders/ord_x8k2J9aQ/refunds -d @refund.json
cat prices.json | pallastrade api post /prices/bulk_upsert -d -
pallastrade api delete /products/prod_86Rf07xd
```

Mutations automatically carry an `Idempotency-Key`, so retries are safe.

### Creating products

A product is a catalog grouping; everything purchasable — SKU, price, stock, weight — lives on its variants. For a **simple product** with no options, ship a top-level `prices` array and PallasTrade creates the single backing variant for you:

```bash
pallastrade api post /products -d '{"name":"Classic Tee","prices":[{"currency":"USD","amount":"29.99"}]}'
```

For a product with options, send the `variants` array, each with its own `options` and `prices` (and optionally `stock_items`):

```bash
pallastrade api post /products -d '{
  "name": "Classic Tee",
  "variants": [
    { "sku": "TEE-S", "options": [{"name":"size","value":"Small"}], "prices": [{"currency":"USD","amount":"29.99"}] },
    { "sku": "TEE-M", "options": [{"name":"size","value":"Medium"}], "prices": [{"currency":"USD","amount":"29.99"}] }
  ]
}'
```

Run `pallastrade api schema "POST /products"` for the full request body.

## Discovering endpoints and schemas

The CLI bundles a snapshot of the Admin API OpenAPI spec, so discovery works offline:

```bash
pallastrade api endpoints --resource orders          # methods, paths, required scopes
pallastrade api endpoints --search "gift card"
pallastrade api schema "POST /orders"                # parameters + request/response schema
pallastrade api status                               # resolved credentials + server reachability
```

`pallastrade api endpoints` shows the `read_*` / `write_*` scope each endpoint requires (see [Authentication](/api-reference/admin-api/authentication)) — useful for deciding what to grant a new key.

### Shell completion

Tab-completion suggests resource paths, Ransack predicate stems (`name_cont=`, `status_eq=`, …), and scope names — all offline from the bundled spec. Add the generated script to your shell:

```bash
# zsh — add to ~/.zshrc
eval "$(pallastrade completion zsh)"
# bash — add to ~/.bashrc
eval "$(pallastrade completion bash)"
# fish — add to ~/.config/fish/config.fish
pallastrade completion fish | source
```

Then `pallastrade api get /pro⇥` completes to `/products`, and `pallastrade api get /products -q name_⇥` offers the Ransack predicates.

## Errors and exit codes

API errors print the error envelope to stderr and exit `1`; usage and configuration problems exit `2`. A scope denial includes the exact remediation:

```text
access_denied: API key lacks scope: write_products
{
  "details": { "required_scope": "write_products" }
}
Hint: mint a key carrying this scope — pallastrade api-key create --type secret --scopes write_products
```

## Using it with AI agents

Agents with shell access (Claude Code, Cursor, and similar) can drive a PallasTrade back office through `pallastrade api` with no extra configuration: inside a project the credentials self-provision read-only, and for remote stores two environment variables (`PALLASTRADE_BASE_URL`, `PALLASTRADE_API_KEY`) are the whole contract. The `endpoints`/`schema` commands give agents request shapes on demand instead of loading the entire API surface up front, and error messages name the missing scope so agents can self-correct.
