In this tutorial, we'll connect our custom Brand model with PallasTrade's core Product model. This is a common pattern when building features that need to integrate with existing PallasTrade functionality.

<Info>
  This guide assumes you've completed the [Model](/developer/tutorial/model) and [Admin](/developer/tutorial/admin) tutorials.
</Info>

## What We're Building

By the end of this tutorial, you'll have:

- Products associated with Brands
- A brand selector in the Product admin form
- Understanding of how to safely extend PallasTrade core models

## Choosing the Right Approach

Before extending PallasTrade models, consider which approach fits your needs best:

| What you need | Recommended approach |
|---------------|---------------------|
| Add association (belongs_to, has_many) | **Decorator** (this tutorial) |
| Add validation or scope | **Decorator** |
| Add new instance/class method | **Decorator** |
| React to model changes (after save, etc.) | [Events subscriber](/developer/core-concepts/events) |
| Sync with external service on changes | [Events](/developer/core-concepts/events) or [Webhooks](/developer/core-concepts/webhooks) |
| Add searchable/filterable field | [Ransack configuration](/developer/core-concepts/search-filtering#extending-ransackable-configuration) |
| Add admin UI elements | [Admin Partials](/developer/admin/extending-ui) |

<Info>
  This tutorial uses **decorators** because we're adding a structural association between models. For behavioral changes like callbacks, prefer [Events](/developer/core-concepts/events) instead - they're easier to test and maintain.
</Info>

## Understanding Decorators

When working with PallasTrade, you'll often need to add functionality to existing models like `PallasTrade::Product` or `PallasTrade::Order`. However, you shouldn't modify these files directly because:

1. **Upgrades** - Your changes would be lost when updating PallasTrade
2. **Maintainability** - It's hard to track what you've customized
3. **Conflicts** - Direct modifications can conflict with PallasTrade's code

Instead, we use **decorators** - a Ruby pattern that lets you add or modify behavior of existing classes without changing their original source code.

### How Decorators Work

In Ruby, classes are "open" - you can add methods to them at any time. Decorators leverage this by:

1. Creating a module with your new methods
2. Using `Module#prepend` to inject your module into the class's inheritance chain
3. Your methods run first, and can call `super` to invoke the original method

```ruby
# This is the basic pattern
module PallasTrade
  module ProductDecorator
    # Add a new method
    def my_new_method
      "Hello from decorator!"
    end

    # Override an existing method
    def existing_method
      # Do something before
      result = super  # Call the original method
      # Do something after
      result
    end
  end

  Product.prepend(ProductDecorator)
end
```

The key line is `Product.prepend(ProductDecorator)` - this inserts your module at the beginning of the method lookup chain, so your methods are found first.

## Step 1: Create the Migration

First, add a `brand_id` column to the products table:

<CodeGroup>

```bash PallasTrade CLI (Docker)
pallastrade generate migration AddBrandIdToPallasTradeProducts brand_id:integer:index
```

```bash Without PallasTrade CLI
bin/rails g migration AddBrandIdToPallasTradeProducts brand_id:integer:index
```

</CodeGroup>

Edit the migration to add an index (but no foreign key constraint, keeping it optional):

```ruby db/migrate/XXXXXXXXXXXXXX_add_brand_id_to_pallastrade_products.rb
class AddBrandIdToPallasTradeProducts < ActiveRecord::Migration[8.0]
  def change
    add_column :pallastrade_products, :brand_id, :integer
    add_index :pallastrade_products, :brand_id
  end
end
```

Run the migration:

<CodeGroup>

```bash PallasTrade CLI (Docker)
pallastrade migrate
```

```bash Without PallasTrade CLI
bin/rails db:migrate
```

</CodeGroup>

<Info>
  We intentionally don't add a foreign key constraint. This keeps the association optional and avoids issues if brands are deleted. PallasTrade follows this pattern for flexibility.
</Info>

## Step 2: Generate the Product Decorator

PallasTrade provides a generator to create decorator files with the correct structure:

<CodeGroup>

```bash PallasTrade CLI (Docker)
pallastrade generate model_decorator PallasTrade::Product
```

```bash Without PallasTrade CLI
bin/rails g pallastrade:model_decorator PallasTrade::Product
```

</CodeGroup>

This creates `app/models/pallastrade/product_decorator.rb`:

```ruby app/models/pallastrade/product_decorator.rb
module PallasTrade
  module ProductDecorator
    def self.prepended(base)
      # Class-level configurations go here
    end
  end

  Product.prepend(ProductDecorator)
end
```

## Step 3: Add the Brand Association to Product

Update the decorator to add the `belongs_to` association:

```ruby app/models/pallastrade/product_decorator.rb {4}
module PallasTrade
  module ProductDecorator
    def self.prepended(base)
      base.belongs_to :brand, class_name: 'PallasTrade::Brand', optional: true
    end
  end

  Product.prepend(ProductDecorator)
end
```

### Understanding the Code

- `self.prepended(base)` - This callback runs when the module is prepended to a class. The `base` parameter is the class being decorated (`PallasTrade::Product`)
- `base.belongs_to` - We call class methods on `base` to add associations, validations, scopes, etc.
- `optional: true` - Products don't require a brand (the `brand_id` can be `NULL`)

## Step 4: Add Products Association to Brand

Now update your Brand model to define the reverse association:

```ruby app/models/pallastrade/brand.rb {5}
module PallasTrade
  class Brand < PallasTrade::Base
    # ... existing code ...

    has_many :products, class_name: 'PallasTrade::Product', dependent: :nullify

    # ... rest of your model ...
  end
end
```

<Info>
  We use `dependent: :nullify` instead of `dependent: :destroy`. When a brand is deleted, products will have their `brand_id` set to `NULL` rather than being deleted. This is safer for e-commerce data.
</Info>

## Step 5: Permit the Brand Parameter

For the admin form to save the brand association, we need to permit the `brand_id` parameter.

Add to your PallasTrade initializer:

```ruby config/initializers/pallastrade.rb {3}
# .. other code ..

PallasTrade::PermittedAttributes.product_attributes << :brand_id
```

## Step 6: Add Brand Selector to Product Admin Form

Create a partial to inject the brand selector into the product form. PallasTrade's admin product form has injection points for customization.

Create the partial:

```erb app/views/pallastrade/admin/products/_brand_field.html.erb
<div class="card mb-6">
  <div class="card-header">
    <h5 class="card-title"><%= PallasTrade.t(:brand) %></h5>
  </div>
  <div class="card-body">
  <%= f.pallastrade_select :brand_id,
      PallasTrade::Brand.order(:name).pluck(:name, :id),
      { include_blank: true, label: PallasTrade.t(:brand) } %>
</div>
```

Register this partial to appear in the product form. Add to your initializer:

<Tabs>
  <Tab title="PallasTrade 5.2+">
    ```ruby config/initializers/pallastrade.rb
    Rails.application.config.after_initialize do
      PallasTrade.admin.partials.product_form_sidebar << 'pallastrade/admin/products/brand_field'
    end
    ```
  </Tab>
  <Tab title="PallasTrade 5.1 and below">
    ```ruby config/initializers/pallastrade.rb
    Rails.application.config.pallastrade_admin.product_form_sidebar_partials << 'pallastrade/admin/products/brand_field'
    ```
  </Tab>
</Tabs>

## Testing the Association

Verify everything works in the Rails console:

```ruby
# Create a brand and product
brand = PallasTrade::Brand.create!(name: 'Nike')
product = PallasTrade::Product.first
product.update!(brand: brand)

# Test associations
product.brand        # => #<PallasTrade::Brand id: 1, name: "Nike"...>
brand.products       # => [#<PallasTrade::Product...>]
brand.products.count # => 1
```

## Decorator Best Practices

<CardGroup cols={2}>
  <Card title="Use prepended callback" icon="code">
    Always use `self.prepended(base)` for class-level additions like associations, validations, and scopes.
  </Card>

  <Card title="Keep decorators focused" icon="crosshairs">
    Each decorator should have a single responsibility. Create multiple decorators if needed.
  </Card>

  <Card title="Call super when overriding" icon="arrow-up">
    When overriding methods, call `super` to preserve original behavior unless you intentionally want to replace it.
  </Card>

  <Card title="Test decorated behavior" icon="flask-vial">
    Write tests specifically for your decorated functionality to catch regressions.
  </Card>
</CardGroup>

### Common Decorator Patterns

#### Adding Validations

```ruby
def self.prepended(base)
  base.validates :custom_field, presence: true
end
```

#### Adding Scopes

```ruby
def self.prepended(base)
  base.scope :featured, -> { where(featured: true) }
end
```

#### Adding Callbacks

<Warning>
  For callbacks that trigger side effects (syncing to external services, sending notifications, etc.), use [Events subscribers](/developer/core-concepts/events) instead of decorator callbacks. Events are easier to test and won't break during PallasTrade upgrades.
</Warning>

**Decorator approach** (use only for simple, internal logic):

```ruby
def self.prepended(base)
  base.before_save :normalize_name
end

def normalize_name
  self.name = name.strip.titleize if name.present?
end
```

**Events approach** (recommended for side effects): subscribe to `product.updated` and react in a `PallasTrade::Subscriber` — no decorator, no callback coupling. The [Events & Webhooks tutorial](/developer/tutorial/events) builds this out fully, including external-system sync (OMS, warehouse) and outbound webhooks.

#### Adding Class Methods

```ruby
def self.prepended(base)
  base.extend ClassMethods
end

module ClassMethods
  def my_class_method
    # Class method logic
  end
end
```
