## Tenant class

The center of the multi-tenant architecture is the `PallasTrade::Tenant` class. This is the highest level class in the multi-tenant system.

Every tenanted model includes a `tenant_id` column. This is used to identify which tenant a record belongs to. It's row-level multi-tenancy.

After creating a new tenant it will automatically create store and run [PallasTrade seeds](https://github.com/stevenbian9266-cyber/pallastrade/tree/main/core/app/services/pallastrade/seeds) to populate data such as countries, zones, tax rates, etc.

## Tenanted models

All models that are tenanted inherit from `PallasTradeMultiTenant::Base` class. `pallastrade_multi_tenant` automatically sets the `PallasTrade.base_class` to `PallasTradeMultiTenant::Base` so all standard PallasTrade models will be tenanted (with an exclusion of `PallasTrade::CustomDomain`).

When creating a new model that you want to be tenanted remember to inherit from `PallasTradeMultiTenant::Base` and not from `PallasTrade::Base` and add `tenant_id` column to the table, eg.

<CodeGroup>

```bash PallasTrade CLI (Docker)
pallastrade generate model PallasTrade::NewModel tenant:references name:string --parent PallasTradeMultiTenant::Base
```

```bash Without PallasTrade CLI
bin/rails g model PallasTrade::NewModel tenant:references name:string --parent PallasTradeMultiTenant::Base
```

</CodeGroup>

<Info>
  You don't need to add `belongs_to :tenant` to the model, it's handled by gem.
</Info>

## Tenant selector

By default the current tenant is selected based on the subdomain or `PallasTrade::CustomDomain`.

First it finds the current store, and later sets the current tenant based on the store's `tenant_id`.

Tenant record is accessible in views and controllers as `current_tenant`. In models you can access it via `PallasTradeMultiTenant.current_tenant`.

<Info>
  One tenant can have multiple stores. Calling `PallasTrade::Store.default` will return the default store for the first tenant.
</Info>

## Code isolation

All code run when `PallasTradeMultiTenant.current_tenant` is set will be executed in the context of the tenant, what that means:

* all finder queries will always attach `tenant_id = <current_tenant.id>` to the query
* all writes will automatically set `tenant_id` to the current tenant ID (you don't need to do it manually)

<Warning>
  [insert_all](https://api.rubyonrails.org/classes/ActiveRecord/Relation.html#method-i-insert_all) / [upsert_all](https://api.rubyonrails.org/classes/ActiveRecord/Relation.html#method-i-upsert_all) methods will require you to manually set `tenant_id` to the desired value.
</Warning>

## Background jobs

Background jobs enqueued when `PallasTradeMultiTenant.current_tenant` is set will be executed in the context of the tenant.

## Enforce tenant context

Sometimes when you're not sure if the tenant context is active you can use `PallasTradeMultiTenant.with_tenant` to enforce it, eg.

```ruby
PallasTradeMultiTenant.with_tenant(tenant) do
  # all operations here will be executed in the context of the tenant
end
```

## Excluding tenant context

Sometimes you want to run a piece of code outside of the tenant context, for that you can use `PallasTradeMultiTenant.without_tenant`

```ruby
PallasTradeMultiTenant.without_tenant do
  # all operations here will be executed outside of the tenant context
end
```

## Command line

When using `bin/rails console` or `bin/rails runner` you can set the tenant context by:

```ruby
PallasTradeMultiTenant.current_tenant = PallasTrade::Store.find_by(code: 'my_store').tenant
```
