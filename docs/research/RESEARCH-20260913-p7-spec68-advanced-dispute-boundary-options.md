## 2. 「advanced dispute capabilities」能力清单（15 个候选）

> 判定口径：**规格允许** = 与 §71「明确不做」无冲突且不违反 §43/§45 的"不自动决策"原则；**规格禁止** = 直接命中 §71；**受阻** = 缺 provider 凭据/契约，无法真实 E2E。

### 2.1 规格**禁止**（若要做，必须先修订 §71）

| # | 能力 | §71 原文依据 | 我的判断 |
|---|---|---|---|
| 1 | 自动抗辩 / 自动提交证据 | ❌ **Automatic Representment** | 不建议 |
| 2 | AI 生成证据内容 | ❌ **AI-generated Evidence Submission** | 不建议 |
| 3 | 争议后自动退款 | ❌ **Automatic Refund after Dispute** | 不建议 |
| 4 | 争议后自动补货 | ❌ **Automatic Inventory Restock** | 不建议 |
| 5 | 自动向客户再收款 | ❌ **Automatic Customer Re-charge** | 不建议 |
| 6 | 早期欺诈预警工作流（Radar EFW） | §16 已排除 P7 Core；§71 ❌ Fraud Engine / Risk Scoring | 不建议 |

### 2.2 **受阻**（需 provider 凭据/契约，当前不可验证）

| # | 能力 | 阻塞原因 |
|---|---|---|
| 7 | 二次申诉 / 仲裁阶段（pre-arbitration、arbitration）状态机 | 需真实 provider 阶段行为契约 |
| 8 | 多 provider 事件与证据类型适配（Adyen / PayPal） | 需 sandbox 凭据 + contract + 真实 E2E（§68 先决条件） |

### 2.3 **规格允许且纯本地可做**（不依赖外部凭据，不触碰 §71）

| # | 能力 | 规格依据 | 说明（做什么 / 不做什么） |
|---|---|---|---|
| 9 | **证据素材库 / 按 reason code 的模板与建议字段** | §41/§42（证据快照不伪造事实） | 提供可复用文本与文件**素材**、按 reason code 提示应填字段；**不生成内容、不自动提交** |
| 10 | **提交前完整性/合规校验** | §43（提交是显式动作）+ §46 能力矩阵 | 提交前校验必填字段/文件类型/大小/期限，给出阻断或告警；**不代替人决策** |
| 11 | **证据版本与回执追踪** | DSP-P7-8 的 `DisputeEvidenceSubmission` 已有 append-only 基础 | 每次提交的记录、provider 回执、后续证据版本对比；只读投影 |
| 12 | **审批 / 复核工作流**（案件分配、双人复核、危险操作二次确认） | §45（不自动代表商户做决策） | 把"人做的决策"编排出流程与留痕；**动作本身仍由人触发** |

| 15 | **与退货/换货（RMA）联动**（人工触发） | §38/§39/§40（库存与订单永不由争议自动改变） | 争议详情页提供"去创建退货/补货单"的入口；**库存与订单变更仍走原有显式流程** |

## 3. 可选边界方案（供你定义）

### 方案 A —「整体挂起」（最小）
- **范围**：不做任何新增；§68 第 5 条保持"未定义"，与第 1、2 条一并挂起。
- **依赖**：无。
- **理由**：规格 §68 先决条件（凭据/契约/E2E）不满足。
- **代价**：争议运营仍靠人工翻查（无素材库、无报表、无流程留痕）。
- **验收**：无需验收（仅记录决策）。

### 方案 B —「本地运营增强」（推荐）
- **范围**：**2.3 全部 7 项**（#9–#15）。
- **明确不含**：2.1 全部（规格禁止）、2.2 全部（受阻）。
- **依赖**：无外部凭据；需要新迁移（证据素材表、审批/分配字段或表）。
- **影响面**：`pallastrade_core`（新模型/服务）+ `pallastrade_admin`（控制台扩展）+ 只读报表端点；**零资金自动化、零账本写扩展**。
- **风险**：低（不触碰资金与库存自动化）；主要风险是"素材库被误解为自动提交"→ 需负向断言锁死。
- **验收判据（模板）**：
  1. 每项能力都有"**不产生任何资金/库存/订单写动作**"的负向断言；
  2. 素材库/模板**只能人工插入**到证据草稿，`SubmitEvidence` 仍是唯一提交入口且需显式确认；
  3. 报表在 mixed currency / 无 payment 锚点等边界下仍降级不报错；
  4. dev 上可端到端演示（无需 provider 凭据）。
- **工作量**：中（约 4–7 个工作包，可拆 PRD）。

### 方案 C —「B + Stripe 深化」
- **范围**：方案 B **+** 按 `reason code` 的证据模板映射（Stripe 场景）+ 提交回执状态机（基于现有 `DisputeEvidenceSubmission`）。
- **依赖**：Stripe（已有测试模式），可做真实 E2E。
- **与 B 的差异**：多一层"按 provider reason code 映射建议字段/素材"的知识层。
- **风险**：低-中（需避免把"建议"做成"自动填充并提交"）。
- **工作量**：中偏上。

### 方案 D —「含 provider 状态机深化」
- **范围**：方案 C **+** 2.2 的 #7、#8（二次申诉/仲裁 + Adyen/PayPal 适配）。
- **阻塞**：**必须先解除 Adyen/PayPal 凭据挂起**（你已确认不处理）→ **当前不可落地**。
- **建议**：不单独启动；与凭据挂起项绑定，等凭据到位后作为 DSP-P7-10 一起做。
