> **写作要求（强制 —— 不满足即打回重写）**
>
> 1. **本模板是下限，不是上限**。每节按真实事实填满，**禁止占位符**（`<...>`、`待补充`、`TBD`）。
> 2. **篇幅**：新功能 ≥ 200 行 · 优化迭代 ≥ 150 行 · Bug 修复 ≥ 100 行。
> 3. **FR ↔ AC 双向完整**：每条 FR ≥ 1 条 AC；每条 AC 必须有**可执行的判定条件** + **测试落点（文件路径）**。
>    不允许用「人工看一下」充当验收。
> 4. **场景必须含边界与异常**：§2.2 的「类型」列至少各出现一次 **边界** 与 **异常**。
> 5. **证据先于结论**：§1.1 每条现象都要给证据（命令输出 / SQL 结果 / 代码位置 / 截图）；禁止「可能是 / 应该是」。
> 6. **写代码前这些节必须已存在**：§9 跨层搜索、§13 风险与回滚、§14 决策记录。
> 7. **节级豁免**：不涉及界面 / 交互 / 数据的需求，在 §4 / §5 / §6 写「**不适用 + 理由**」（不是留空）；
>    仅 **Bug 修复**可整节省略 §6 数据与埋点、§14 决策记录、§15 开放问题（写「本节不适用：<原因>」）。
>    其余节任何情况不得删除。
> 8. **功能详述深度**：每条 **P0 FR** 必须在 §3.2 展开八要件（触发与入口 / 前置条件 / 主流程 / 分支与边界 /
>    异常处理 / 后置状态 / 权限 / 验收映射）；P1 / P2 至少「触发 / 主流程 / 异常」三项。禁止只写总表。
> 9. **界面三件套**：涉及界面必须给出 ① 状态矩阵（loading / empty / error / success / 禁用）
>    ② 文案与 i18n key ③ 设计 token 引用；**禁止硬编码色值 / 字号 / 间距**（AP-001 / AP-006）。
> 10. **交互异常纪律**：§5.3 至少覆盖「超时 / 并发 / 权限不足」中实际适用者；失败路径遵守 AP-009
>    （降级 UI 不得静默吞错、不得触发重定向死循环）。
> 11. **无设计稿时**：以现有组件库 / 邻近页面为视觉基线，所有推断项登记到 §15 开放问题。
> 12. **示例与编号纪律**：示例编号一律写 `AC-xxx` / `FR-xxx` 形式，或整段放 HTML 注释（`<!-- 示例：… -->`）。
