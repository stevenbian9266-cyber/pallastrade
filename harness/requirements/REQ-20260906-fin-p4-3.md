## 需求标题

FIN-P4-3：Payment/Refund Posting —— payment.paid / refund.created → FinancialLedger::PostPayment/PostRefund 入账接线（P4 拆包第 3 包）。

## 任务类型

新功能（core gem 服务 + subscriber + engine 注册；**无 migration、无 API/UI**）

## 需求描述

在 FIN-P4-1（FinancialFact 解析）与 FIN-P4-2（FinancialLedger::Post 幂等原语）之上建立业务接线：新增 `FinancialLedger::PostPayment`/`PostRefund` 编排（ResolvePayment/ResolveRefund → 门禁 → Post；不可 post 的 fact → `success({ entry: nil, skipped: true, reason })`，不猜不记）；新增 `PaymentPaidSubscriber`（subscribes_to 'payment.paid'，Payment::CustomEvents after_commit 发布）与 `RefundCreatedSubscriber`（subscribes_to 'refund.created'，lifecycle after_commit）→ 注册到 core engine.rb subscribers.concat。posting 恒在资金事务提交后执行（after_commit），失败不影响 Payment/Refund（subscriber rescue + 日志，幂等 key 保重试安全）。不创建/更新 Payment/Refund、不改 state machine、不改 Settlement/Carts/P0-P3 任何行为。覆盖 single / balance collection / combination（1 Payment → 1 cash entry；split allocation 归 P4-4）。

## 影响范围

- 变更：core gem `app/services/pallastrade/financial_ledger/`（新增 2）+ `app/subscribers/pallastrade/financial_ledger/`（新增 2）+ `lib/pallastrade/core/engine.rb`（注册 2）+ `backend/spec/**` 新增 + skills/scenarios/PRD。
- 不改：Payment/Refund/Settlement/Carts/Transactions/OrderUpdater/PaymentSplit；无 migration/schema；无 API/storefront/platform。

## 技术方案（初步）

见 PRD §7。编排：`PostPayment(payment:)` = ResolvePayment → fact；`fact.fact_type ∈ ENTRY_TYPES && confirmed? && commerce_transaction_id.present?` 才 Post；否则 skipped success（reason 区分）。subscriber 参照 PaymentSessionReservationSubscriber 双模式解析 payload id（`py_`/`re_` 前缀 find_by_param，否则 find_by(id:)）；handler 内 rescue StandardError → Rails.logger.error（不阻断发布方）。

## 风险点

- 最高风险：posting 与支付流耦合（ledger 失败逆转入账）→ 事件后置（after_commit）+ subscriber 独立异步 + rescue，天然隔离；spec 验证 payment 完成不因 posting 失败回滚。
- 中风险：事件重复/重放重复入账 → FinancialLedger::Post idempotency_key（P4-2 已冻结）。
- 低风险：payload id 解析失败 → 静默跳过 + 日志（AC-4P3-09 精神）。
- 回滚难度：低（新增文件 + 注册行；无既有行为变更）。
