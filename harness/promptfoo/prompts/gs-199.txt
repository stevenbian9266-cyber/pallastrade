# Eval Scenario GS-199: Route a payment method to exactly one provider - hard gates first, then a deterministic priority, and never guess what you cannot know

A store runs two providers that both offer cards. The storefront shows the shopper 'card' once, but nothing in the system decides which provider actually takes that payment: the first configured provider wins by accident, a provider that is switched off or has an open breaker can still be picked, a method the merchant account never opened looks available, and a provider that cannot serve this particular order (market scope, authentication requirement) is chosen anyway and fails at the money step. There is also no way to say 'for this market, prefer provider B', and no record explaining why a given payment went where it went. The ask: add a method-level routing decision that applies the same gates the storefront applies, ranks the survivors by an explicit priority, and returns an explainable, reproducible decision.

## MUST do
- Decide routing per payment method (never per provider), so the shopper sees each method once and exactly one provider carries it
- Apply hard gates before any ranking: the method must be configured and enabled on that provider, the provider must be in the enabled state, the merchant account must have the method opened, and the shared availability resolver must agree the option can serve this order
- Reuse the storefront availability evaluation for the last gate instead of writing a second filter, so 'routed' and 'payable' can never disagree
- Rank the survivors by an explicit priority sequence with a per-market override that beats the global sequence, then by the option position, then by a stable identifier so the outcome is reproducible
- Report the basis of the choice (priority override versus position) and keep the full candidate list with ranks plus a rejection list that names the reason for every provider that lost
- Keep the decision read-only - no writes, no provider calls, no payment, session or ledger side effects - and answer no_candidate with no chosen provider when nothing survives, rather than falling back to a default provider
- Keep the mode honest: only off, shadow and priority-only are supported, and a mode that would rank by cost is normalized to off and flagged as unsupported instead of pretending to apply a cost model
- Return the same decision for the same order, method and policy, and record the policy version and the inputs snapshot with the decision
- Make the policy writable through a whitelisting primitive that rejects an unimplemented mode, a provider that does not belong to the store, and a market key that is not the store's, keeps an identical write a no-op without touching the store record's timestamp, and changes no money records
- Provide a preview that reuses the decision's candidate assembly and ranking but explicitly declares that order-scoped gates were skipped, so nobody reads it as 'this will definitely be payable', listed per method with the rejected providers and their reasons and never inventing a method
- Surface that preview in the provider's own admin card so an operator can see, for every method the provider takes part in, who carries it, which position this provider holds and by which basis, or the exact reason it is not a candidate - with copy that repeats that order-scoped gates were not evaluated

## MUST NOT do
- Rank before gating, or let a disabled, suspended or account-unopened provider remain a candidate
- Duplicate the availability rules in the routing layer, or pick a provider for a method the storefront never offered
- Fall back to a default provider when no candidate survives, or pick by insertion order without saying so
- Apply a cost or health heuristic that the system cannot actually compute, or let shadow mode change what the storefront shows
- Write routing state into money records, or treat a routing decision as a settlement fact
