# Eval Scenario GS-119: Request order is part of the contract — payment combinations keep the first requested order as primary

2026-09-14 bugfix: POST /api/v3/store/payment_combinations resolved order_ids with an unordered where(id: ...), so the primary order varied by database row order and the payment session could attach to a member order instead; this surfaced as an order-dependent spec failure that blocked evidence collection repeatedly and hid a genuine behaviour defect

## MUST do
- Preserve the caller-supplied order when resolving a batch of prefixed ids (index the queried rows by id, then rebuild the list in the requested order)
- Treat order_ids.first as the primary order and create its payment session there, and pin that contract with a test that passes the ids in reverse order
- When an order-dependent failure appears, treat it as a product defect candidate (unstable primary/selection) before labelling it a flake and re-running

## MUST NOT do
- Return `where(id: [...])` (or any unordered set) where the caller's ordering carries meaning
- Re-run a repeatedly failing spec until it passes without identifying why the outcome varies
