# Eval Scenario GS-167: Observability that cannot block the thing it observes

The AI draft flow already recorded whether a draft was accepted or discarded, but not whether the merchant rewrote it before saving — the number that tells you whether the output was actually usable. Recording it means measuring a form the merchant is about to submit, which is exactly where a logging call can quietly turn into a save guard.

## MUST do
- Take the snapshot after the draft is written into the form, or every save reports an edit
- Compare the values that were written rather than whether the form was touched, or editing an unrelated field reads as a rewrite
- Report at most once per decision, and clear the snapshot so a repeated submit does not double count
- Keep the request alive across the navigation the submit triggers
- Swallow report failures completely — observability never gets to block a save

## MUST NOT do
- Let a failed or slow report change what the merchant sees
- Infer 'edited' from focus or input events instead of comparing values
- Leave a stale snapshot in place so a later save of an unrelated form reports an edit
- Declare the frontend untestable and assert nothing — pin the four behaviours at source level instead

## Scoring
- nonBlocking: 30
- noFalsePositives: 25
- snapshotTiming: 20
- reportOnce: 15
- honestTestCoverage: 10
