# Eval Scenario GS-198: Make the provider layer honest - declare capability, record the merchant account, narrow the three sets, and explain every mismatch

A store runs several payment providers. The admin only stores 'which storefront options are enabled', so the operator cannot tell the difference between 'the provider supports this method', 'our merchant account has it opened' and 'we restricted it to these markets'. The save path silently drops anything it does not recognise, so a mistyped option kind or an out-of-scope currency looks saved while the storefront quietly never offers it; there is no place to record what the PSP account actually has enabled, and provider state is split between a boolean and a circuit breaker with no single answer to 'can this provider take money right now, and why not'. The ask: add a provider layer that declares static capability, records the account side (manual or synced), narrows capability against account and market, and surfaces every mismatch as a readable diagnosis without changing the write path yet.

## MUST do
- Treat an existing configured provider record as the provider itself instead of inventing a parallel provider table, and keep the account side in the same metadata store the other payment features already use (no migration)
- Read static capability from a provider-declared class-level declaration when present, and only fall back to the method catalog plus session requirement, marking which source answered
- Normalize the account block defensively: unknown keys and malformed lists are ignored rather than raising, kind lists are downcased and de-duplicated, ISO codes upper-cased, timestamps parsed, and a bogus source falls back to manual
- Model 'not declared' as nil (do not narrow that dimension) instead of an empty list, so an unconfigured account can never be read as 'everything is enabled'
- Expose the narrowing as capability intersected with account per dimension, and report the basis (capability only, account only, both, or undeclared) next to the value
- Derive one three-state answer per provider (enabled, disabled, suspended) with the precedence manual disable over breaker over enabled, keep manual disable sticky so clearing a breaker never re-enables a provider a human switched off, and allow auto-recovery only for a timed breaker
- Return diagnostics as structured severity plus code plus params, covering an enabled option the provider never declared, an enabled option the account has not opened, currencies and countries outside the narrowed sets, an amount range beyond the declared limits, a disabled provider that still has enabled options, an optionized provider with nothing enabled, and a partially suspended provider
- Keep the diagnosis itself read-only - no provider calls, no payment, session or ledger side effects - and render it on the existing payment method edit page as a card with the provider state badge, the capability and account sources, the narrowed lists, the configured markets and the issue list
- Make the account side editable from that same card through a dedicated member action that whitelists methods against the declared capability and currencies and countries against the store, reports rejected values back to the operator instead of dropping them silently, treats an empty selection as undeclared (no narrowing) rather than nothing allowed, keeps an identical write idempotent, and audits the change with counts only
- Keep the write path honest about what a declaration means: a provider that declares capability without listing methods still falls back to its method catalog, a non-optionized provider's implicit entry is not compared against the method list, and declared facts the framework does not explain yet are carried through instead of being dropped
- Leave the write path and the existing silent normalization untouched, and say so explicitly, so the new layer adds explainability without changing behaviour or breaking the shipped option-configuration specs
- Register a verifier that runs the provider-layer service specs together with the admin diagnostics request spec, and document the provider layer (sources, narrowing, three-state, stickiness, zero side effects) in the payments skill

## MUST NOT do
- Create a second provider model beside the configured payment method record, or store provider capability and account data in a new table when metadata is the established pattern
- Guess capability from the method catalog when the provider declares it, or read a missing account block as 'all methods, currencies and countries are available'
- Raise on malformed metadata in a read path, or narrow a dimension whose other side is undeclared and silently report the result as an intersection
- Let clearing a breaker re-enable a provider that was manually disabled, or answer the state question from the boolean alone while an open breaker is ignored
- Write configuration, call the provider or touch payment, session or ledger rows from the diagnostics path
- Change the save path to reject configuration in this slice, or hide mismatches in a log line instead of surfacing them in the admin UI
