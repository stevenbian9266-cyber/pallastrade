# Eval Scenario GS-130: Payment availability scope evaluated by one shared resolver

PRD-20260915-payments-d8 (D8 first slice): a payment option (kind) can be scoped by market / country / zone / currency through an entry-level `rule_set` stored in the payment method metadata — the storefront list, the admin back-end list and `PaymentSessions::Start` must all evaluate it through the same `PallasTrade::Payments::Availability::Resolver`, and the admin payment-method tab gains a scope editor plus a human summary.

## MUST do
- Store the rule set as additive JSON: `metadata['options'][i]['rule_set'] = { match: 'all'|'any', include: [ { dimension, operator, values } ], exclude: [...] }` with dimensions market/country/zone/currency and operators in/not_in/eq — normalized on read and write (market/zone raw ids, country/currency uppercase ISO, invalid dimensions/operators/blank values dropped, both sides empty => nil = available everywhere)
- Evaluate through `Availability::RuleSet` + `Context` + `Evaluator` + `Resolver`: exclude wins over include, `match: any` needs one include hit, unresolvable observed values never match, and the resolver additionally narrows by provider scope (frontend/back_end) and the provider capability catalog (declared currencies/countries)
- Route every consumer through the resolver — `Order#payment_methods`, `collect_frontend_payment_methods`, `collect_backend_payment_methods` — so no caller re-implements the rule semantics
- Re-check the requested option inside `PaymentSessions::Start` (option kind -> available options) and fail with `payment_option_not_available` without creating a session when the option is out of scope
- Expose the scope in the admin API as `options[].rule_set` (normalized) plus `options[].scope_summary` (i18n dimension names), and refresh generated contracts via `scripts/ci/contracts.sh` instead of hand-editing SDK types
- Accept prefix ids in the admin form (`mkt_`/`zone_`) but persist raw ids, validating markets against the provider store and countries/currencies against real ISO data plus the store supported-currency list
- Cover the behaviour with the registered `d8-availability-rspec` verifier (resolver + order projection + start gate + admin scope editing)

## MUST NOT do
- Let the storefront list, the admin list and Start compute availability from different code paths (that is the 'selectable but unpayable' failure mode)
- Treat an unknown context as available through the include branch (or unavailable through the exclude branch) — observed values that cannot be resolved must not match
- Persist prefix ids, lowercase ISO codes or capability-unknown dimensions into the rule set, or keep a rule when every submitted value was dropped (empty scope = 不限)
- Drop pre-existing `exclude` conditions when the admin form only manages include conditions
- Change behaviour for providers without a rule set, non-optionized providers or stores without markets (zero-regression behaviour must stay identical)
