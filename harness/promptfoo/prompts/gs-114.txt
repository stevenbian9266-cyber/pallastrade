# Eval Scenario GS-114: Cart discount codes resolve for canonical carts and are redeemed (or refused) at submit

PRD-20260914-checkout-cart-discount-codes-canonical: POST/DELETE /carts/:cart_id/discount_codes resolves cart_ ids through current_store.shopping_carts (storefront and SDK unchanged) while legacy order-backed ids keep the old resolver, the code is stored as an intent on cart.private_metadata and merely validated on apply, and Carts::Submit re-applies it through PromotionHandler::Coupon and fails the submission when the code is no longer valid (RESEARCH-20260913 §9.1 P0-e)

## MUST do
- Resolve cart_... ids through current_store.shopping_carts (guest/user scoped) instead of the order-backed resolver that answered 403 access_denied
- Persist the applied code as cart intent (private_metadata.discount_code), normalised for case and whitespace, and keep removal idempotent
- Validate only on apply (coupon_code_not_found / coupon_code_expired) because applying a code must never consume it — reservation and commitment belong to PromotionRedemption
- Re-apply the stored code in Carts::Submit through PromotionHandler::Coupon before the amount pipeline, and fail the submission (no Order created) when the code is no longer valid
- Log the legacy resolution path so convergence work is driven by real traffic instead of guesses
- Keep the contract in sync: OpenAPI store.yaml twice (backend + platform docs) and the api-v3 skill, with rspec covering both the endpoint and the submit path

## MUST NOT do
- Leave a documented cart_ endpoint routed only through the legacy resolver (the docs promised cart_ support while the implementation returned 403)
- Silently drop an invalid coupon at submit and charge full price, or consume/redeem the code at apply time
- Add a coupon_code column to pallastrade_carts when the intent already fits private_metadata
