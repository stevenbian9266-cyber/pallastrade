# Eval Scenario GS-042: One-click checkout payment saga and unified result

Unified checkout renders provider-owned card fields immediately without creating an Order, then one Pay command updates/submits the Cart, starts or reuses an Order session, confirms Stripe, and opens a server-authoritative success/failed/canceled/pending result. Account cashier targets existing Orders only.

## MUST do
- Render CardPaymentForm before Pay without creating an Order or PaymentIntent
- Use a same-origin BFF and typed SDK for Cart update → replay-safe submit → Order session start; retain a recoverable order_id after post-submit failures
- Confirm Stripe in the same Pay handler and navigate every outcome to /payment-result/[or_|pcom_]
- Reuse matching active PaymentSessions, call providers outside database transactions, and pass stable Stripe operation keys
- Allow an owned completed order with balance_due through the ownership-scoped order payment-session endpoint while keeping other customers' orders hidden
- Publish UnifiedCheckout and OrderPaymentContent summaries through CheckoutContext setSummaryContent
- Add Vitest component coverage and a Store API request authorization regression spec

## MUST NOT do
- Create a browser SDK client or expose server payment credentials
- Redirect a newly submitted Cart to an or_ checkout page that requires a second Pay
- Keep a database transaction open during Stripe/PayPal/Adyen network I/O
- Use generic completed-order update permission to gate payment-session creation
- Render a second nested desktop summary sidebar inside the checkout layout main column
- Remove current-store and current-customer/token order isolation
- Skip objective UI and API regression evidence
